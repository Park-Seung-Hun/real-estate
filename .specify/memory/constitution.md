# 아파트 임장 기록과 실거래 알림 Constitution

MUST와 SHOULD는 규칙의 강도이고, `/speckit-analyze`는 MUST 위반을 CRITICAL로 판정합니다. 원칙마다 붙인 점검 질문은
plan의 Constitution Check에서 답합니다. 위반을 처리하는 방법은 Governance에 있습니다.

## Core Principles

### I. 공식 API만 사용

- **MUST** 외부 데이터는 기관이 공개하는 공식 API에서만 수집합니다.
- **MUST** 부동산 앱 화면 수집, 매물 호가 수집, KB 시세 수집을 하지 않습니다. 매물 링크를 받아 서버가 그 페이지를 읽는
  방식도 화면 수집에 해당합니다.
- **MUST** 블로그, 카페, 앱 후기는 저장하지 않습니다.

점검: 이 기능이 공식 API가 아닌 곳에서 데이터를 가져오는가? 매물 링크의 페이지를 서버가 읽는가? 후기를 저장하는가?

이유: 호가와 KB 단지별 시세는 개인이 쓸 수 있는 공식 API가 없고, 시세 공개 기관과 검색 API의 이용 조건이 자동 수집이나
결과 저장을 금지하기 때문입니다. 공식 API에 없는 호가와 KB 시세는 사용자가 직접 입력합니다
([결정 기록 0001](../../docs/adr/0001-official-api-only.md)).

### II. 자체 화면 입력

- **MUST** 임장 기록, 매물, 호가는 서비스 자체 화면에서 사용자가 입력합니다. 1단계 화면은 휴대폰 화면 폭을 기준으로 한
  웹입니다.
- **MUST** 노션 연동과 기존 노션 기록 옮기기는 범위에 넣지 않습니다.

점검: 이 기능이 외부 서비스(노션 등)에서 기록을 읽어 오거나 옮기는가? 휴대폰 화면 폭에서 쓸 수 없는 화면을 만드는가?

이유: 노션 연동은 기록이 정해진 템플릿 구조여야 읽어 올 수 있어 아직 고려 대상이 아니기 때문입니다
([결정 기록 0002](../../docs/adr/0002-own-input-screen.md)).

### III. 실제 데이터를 저장소에 두지 않음

- **MUST** 실제 임장 기록, 주소, 사진, API 인증키는 저장소에 올리지 않습니다. 인증키는 환경 변수나 `.env`(저장소 추적
  제외)에 둡니다.
- **MUST** 문서의 예시, 테스트 fixture, 시드 데이터는 가짜 단지명과 가짜 주소로 만듭니다.
- **MUST** 공개 문서에는 실제 관심 지역 이름 대신 "관심 지역"이나 "한 자치구"를 씁니다.
- **MUST** 커밋 전에 실제 데이터와 인증키가 섞이지 않았는지 확인합니다.

점검: 이 기능의 fixture, 시드, 예시, 설정 파일에 실제 기록, 주소, 사진, 관심 지역, 인증키가 들어가는가? 인증키를 환경
변수나 `.env` 밖에 두는가? spec, plan 같은 공개 문서에 실제 관심 지역 이름을 쓰는가? tasks에 커밋 전 실제 데이터와
인증키 확인이 있는가?

이유: 이 저장소는 공개 저장소이기 때문입니다.

### IV. 설계 문서를 따름

- **MUST** 기능의 `contracts/`는 [API 공통 규칙](../../docs/architecture/api-conventions.md)을 따릅니다.
- **MUST** 기능의 `data-model.md`는 [데이터 모델](../../docs/architecture/data-model.md)을 참조하고, 그 기능이 다루는
  테이블만 적습니다.
- **MUST** 용어는 [설계 문서 지도의 용어 표](../../docs/README.md#용어)를 따릅니다. 표에서 쓰지 않기로 한 이름을 spec,
  plan, 코드 주석에 쓰지 않습니다.
- **MUST** 설계 문서와 다른 결정이 필요하면 구현보다 먼저 결정 기록(`docs/adr/`)을 수정하거나 새로 씁니다.
- **MUST** 기능은 [백로그](../../docs/backlog.md)의 순서와 경계를 따릅니다.

점검: 계약이 API 공통 규칙과 다른가? `data-model.md`에 이 기능이 다루지 않는 테이블이 있거나 데이터 모델과 다른가? 용어 표에서
쓰지 않기로 한 이름을 사용하는가? 설계 문서와 다른 결정을 결정 기록보다 먼저 구현하는가? 백로그가 정한 순서와 이 기능의 경계를
벗어나는가?

이유: 설계 문서가 정한 규칙(권한 확인 순서, 기준 적재, 삭제 연쇄 등)이 기능마다 다르게 다시 정해지면 기능 사이에서
어긋나기 때문입니다.

### V. 기능마다 테스트

- **MUST** 기능마다 spec의 acceptance를 검증하는 테스트를 둡니다. 검증할 수 없는 acceptance는 spec 단계에서 수정합니다.
- **MUST** tasks에 acceptance마다 그것을 검증하는 테스트 작업을 둡니다.
- **MUST** 보안 경계(권한 확인, 재인증, 삭제 연쇄)를 검증하는 테스트는 그 기능을 구현한 사람이나 에이전트와 다른 사람이나
  에이전트가 요구사항에서 직접 씁니다.
- **MUST** 데이터베이스가 걸린 테스트는 데이터베이스를 목이나 다른 데이터베이스로 대체하지 않고 실제 PostgreSQL로
  실행합니다.
- 테스트를 먼저 쓰는 순서(TDD)는 강제하지 않습니다.

점검: 검증할 수 없는 acceptance가 spec에 남았는가? acceptance마다 그것을 검증하는 테스트 작업이 tasks에 있는가? 보안 경계
테스트를 구현과 다른 쪽이 쓰는가? 데이터베이스를 목이나 다른 데이터베이스로 대체한 테스트가 있는가?

이유: 구현과 테스트를 같은 사람이나 에이전트가 쓰면 요구사항을 잘못 읽었을 때 테스트도 같은 오해를 담아 통과하기
때문입니다. [데이터 모델](../../docs/architecture/data-model.md)은 PostgreSQL을 전제로 쓰였습니다(`user` 예약어 인용,
유니크 제약이 빈 값(NULL)을 다루는 방식). 실제 PostgreSQL 규칙, 보안 경계 테스트를 나누는 규칙, TDD를 강제하지 않는 것은
2026-11-03 저장소 소유자 결정입니다.

### VI. 결정 없이 미리 만들지 않음

- **MUST** 결정 기록이나 설계 문서가 정하지 않은 확장 지점(지금 기능이 쓰지 않는 인터페이스, 설정, 분기)을 만들지 않습니다.
  결정 기록이 정한 확장 지점([결정 기록 0003](../../docs/adr/0003-notification-channel.md)의 "발송 채널을 별도 모듈로
  분리")은 예외입니다.
- **SHOULD** Spring이 제공하는 기능을 감싸기만 하는 계층을 두지 않고 직접 사용합니다. 결정 기록이 정한 계층
  ([결정 기록 0013](../../docs/adr/0013-session.md)의 Spring Session 해시 저장 래퍼 등)은 해당하지 않습니다.

점검: 이 plan에 결정 기록이나 설계 문서가 정하지 않은 확장 지점이 있는가? 결정 기록이 정하지 않았는데 Spring 기능을
감싸기만 하는 계층이 있는가?

이유: [결정 기록 0004](../../docs/adr/0004-staged-adoption.md)가 Kafka, Redis, Kubernetes에 적용한 "측정한 뒤 도입"
기준을 코드 구조에도 적용합니다(2026-11-03 저장소 소유자 결정). 프레임워크를 직접 사용하는 규칙은 SpecKit 방법론 문서의
Article VIII(Framework Trust)를 참고했습니다(https://github.com/github/spec-kit/blob/v1.2.6/spec-driven.md).

## 기술 제약

- **MUST** 서버는 Java와 Spring Boot, 데이터베이스는 PostgreSQL입니다([C4 컨테이너](../../docs/architecture/c4-container.md)).
- **MUST** 1단계와 2단계는 API 서버, collector, 알림 발송기를 한 애플리케이션 안의 모듈로 실행합니다
  ([결정 기록 0005](../../docs/adr/0005-modular-monolith.md)).
- **MUST** Kafka, Redis, Kubernetes 같은 기술은 [결정 기록 0004](../../docs/adr/0004-staged-adoption.md)의 단계와 도입
  조건을 측정한 뒤에 들입니다. 조건을 측정하지 않은 채 앞당겨 넣지 않습니다.
- **MUST** 기반 스택은 [결정 기록 0016](../../docs/adr/0016-base-stack.md)을 따릅니다. Java 25, Spring Boot 4.1, Gradle, Flyway를 사용하고, 데이터는 Spring Data JPA를 기본으로 접근합니다. 잠금, 대량 반영, 집계처럼 JPA가 어색한 곳은 SQL을 직접 사용할 수 있고, QueryDSL은 첫 동적 조회가 필요한 기능에서 도입합니다.
- **MUST** 웹 화면 기술은 이 문서에서 정하지 않습니다. 화면이 처음 나오는 기능의 plan에서 정하고 결정 기록으로 남깁니다.

점검: 이 plan이 Java, Spring Boot, PostgreSQL 밖의 서버 기술을 사용하거나, 결정 기록 0016이 정한 스택과 다른 버전이나 데이터 접근 기술을 쓰거나, 1, 2단계에 모듈을 따로 실행하거나, 도입 조건을
측정하지 않은 Kafka, Redis, Kubernetes를 넣거나, 웹 화면 기술을 결정 기록 없이 정하는가?

## 개발 흐름

- 기능 개발 흐름(SpecKit 명령 순서, 구현 방식)과 브랜치 규칙은 저장소의 `CLAUDE.md`를 따릅니다.
- 기능 브랜치 `NNN-기능이름`은 `develop/vN`에서 만들고, 이름은 `specs/` 아래 폴더 이름과 같습니다. 기능 번호와
  순서는 백로그를 따르고, 번호는 `develop/vN`의 `specs/`에 있는 마지막 번호 다음을 씁니다.

## Governance

- 이 문서는 기능의 spec, plan, tasks, 구현보다 우선합니다. 어긋나면 이 문서에 맞추거나, 이 문서를 먼저 수정합니다.
- 이 문서는 `docs/*` 브랜치에서 수정하고, 수정할 때마다 버전을 올립니다. 원칙을 빼거나 뜻을 바꾸면 MAJOR, 원칙이나 절을
  추가하면 MINOR, 문구만 다듬으면 PATCH를 올립니다.
- 개정할 때는 개정 이유를 커밋 메시지에 적고, 저장소 소유자의 승인을 받아 커밋합니다. 이미 있는 기능(머지하지 않은 기능
  브랜치 포함)의 spec, plan, tasks가 새 규칙과 어긋나는지 확인하고, 어긋나는 기능은 커밋 메시지에 적은 뒤 그 기능을 다음에
  수정할 때 맞춥니다.
- 각 기능의 plan 단계(Constitution Check)에서 모든 원칙의 점검 질문에 답합니다. 지키지 못하는 원칙이 있으면 이유를 plan의
  Complexity Tracking 표에 적습니다. 그 표에 이유가 있는 위반을 `/speckit-analyze`가 CRITICAL로 내면, 저장소 소유자가
  수정할지 예외로 둘지 판단합니다.
