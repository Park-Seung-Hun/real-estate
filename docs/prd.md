# PRD: 아파트 임장 기록과 실거래 알림

아파트를 사려는 본인과 가족 구성원이 임장 기록, 매물 호가, 매매 실거래를 한곳에서 보고, 관심 단지에 거래가 신고되면 알림을 받는 서비스입니다. 이 문서는 서비스가 누구를 위해 무엇을 어디까지 하는지 정합니다.

## 문제

- 임장 기록과 그 단지의 실거래 정보가 서로 다른 곳에 있습니다. 기록을 다시 볼 때마다 시세를 따로 찾아봐야 합니다.
- 매물 호가는 여러 부동산 앱과 중개사무소에서 따로 확인합니다. 호가가 언제 얼마로 바뀌었는지 한곳에 남지 않습니다.
- 임장한 단지에 새 거래가 신고되거나 기존 거래가 해제되어도 직접 찾아보기 전에는 알 수 없습니다.
- 대출 가능 금액과 필요 자기자본은 규제가 바뀔 때마다 달라집니다. 매물마다 다시 계산하기 번거롭습니다.

## 사용자

| 항목 | 내용 |
|---|---|
| 사용자 | 본인과 가족 구성원, 두 명 |
| 사용 환경 | 웹 브라우저. 휴대폰 화면 폭을 기준으로 만들고, 임장 현장에서 휴대폰으로 바로 입력합니다 |
| 찾는 집 | 관심 지역(한 자치구)의 아파트 매매. 전월세는 찾지 않습니다 |
| 함께 보는 방식 | 두 사람이 같은 매물과 기록을 보고, 평가와 메모는 각자 남깁니다 |

## 핵심 시나리오

| # | 시나리오 | 단계 |
|---|---|---|
| 1 | 관심 지역 단지의 최근 5년 매매 실거래 추이를 보고 임장 후보로 추가합니다 | 실거래 추이 1, 단지 기본 정보(세대수, 관리비) 2 |
| 2 | 방문할 매물을 예약하며 호가, 동호수, 전용면적, 위치(지도), 방문 일시를 저장하고 하루 전 알림을 받습니다 | 1 |
| 3 | 매물의 호가 변화를 출처와 함께 이력으로 남기고, 같은 단지, 같은 면적의 최근 실거래와 차이를 봅니다 | 1 |
| 4 | 현장에서 체크리스트, 사진, 메모, 점수를 가족이 각자 남깁니다 | 1 |
| 5 | 본 매물들과 두 사람의 평가를 나란히 비교합니다 | 2 |
| 6 | 예약하거나 기록한 단지에 새 거래나 해제가 신고되면 메일을 받습니다. 같은 면적, 같은 층이면 본 매물이 계약됐을 수 있다고 표시합니다 | 메일 알림 1, 계약 추정 표시 2 |
| 7 | 관심 지역의 새 청약 공고 알림과 접수 전날 알림을 받습니다 | 2 |
| 8 | 자금 프로필과 매물 값으로 기준 날짜의 규제에 맞춰 대출 가능 금액과 필요 자기자본을 계산합니다 | 2 |

- 여러 시나리오가 함께 사용하는 기능은 세 가지입니다. 하루 전 일정 알림(시나리오 2, 7), 매물과 실거래를 단지, 면적, 층 기준으로 연결하는 기능(시나리오 3, 6), 나란히 보기(시나리오 3, 5)입니다.
- 시나리오 6의 알림은 매물 알림이 아니라 이미 계약된 거래의 알림입니다. 실거래 신고 기한이 계약 후 30일이라 새 거래 알림은 계약일보다 한 달 가까이 늦게 올 수 있고, 해제 알림은 더 늦을 수 있습니다.

## 기능 범위

단계는 서비스를 만들어 가는 순서입니다.

| 단계 | 뜻 |
|---|---|
| 1 | 임장 기록과 거래 알림을 실제 임장에 사용할 수 있는 최소 구성 |
| 2 | 단지 정보, 비교, 청약 알림, 자금 계산, 운영 관측을 추가한 구성 |
| 3 | 수집, 알림 발송, 배포 구조를 바꾸는 단계 |
| 4 | 실거래 범위를 서울 전체로 넓히고 조회 성능을 개선하는 단계 |

3단계와 4단계의 기술은 도입하기 전에 도입 조건을 측정하고, 그 결과를 결정 기록에 남깁니다.

| 기능 | 내용 | 단계 |
|---|---|---|
| 로그인과 가족 공유 | 두 사람이 각자 로그인하고 같은 매물과 기록을 함께 봅니다 | 1 |
| 매물 등록과 방문 일정 | 호가, 동호수, 전용면적, 위치(지도), 방문 일시, 상태(검토 중, 보류, 포기, 계약)를 저장합니다. 방문 하루 전에 알림을 보냅니다 | 1 |
| 호가 직접 입력과 이력 | 사용자가 호가를 직접 입력하고 출처를 목록에서 고릅니다. 가격이 바뀌면 덮어쓰지 않고 날짜와 함께 이력으로 남깁니다 | 1 |
| 임장 기록 | 체크리스트, 사진, 메모, 점수를 두 사람이 각자 남깁니다 | 1 |
| 실거래 수집과 추이 | 관심 지역의 아파트 매매 실거래를 최근 5년치 수집하고, 단지별 추이를 표시합니다. 단지를 임장 후보로 추가할 수 있습니다 | 1 |
| 호가와 실거래 비교 | 매물의 호가와 같은 단지, 같은 면적의 최근 실거래를 나란히 표시합니다 | 1 |
| 거래 알림(메일) | 관심 단지에 새 거래나 해제가 신고되면 메일을 보냅니다 | 1 |
| 단지 기본 정보 | 세대수, 준공 연도, 층수, 주차 대수, 난방 방식, 관리비를 공공데이터에서 수집해 단지 화면에 표시합니다 | 2 |
| 매물 비교 | 본 매물들과 두 사람의 평가를 나란히 표시합니다 | 2 |
| 계약 추정 표시 | 새 거래가 본 매물과 같은 면적, 같은 층이면 그 매물이 계약됐을 수 있다고 표시합니다 | 2 |
| 청약 알림 | 관심 지역의 새 청약 공고와 접수 전날 알림을 보냅니다 | 2 |
| 자금 계산 | 아래 자금 계산 절의 입력과 규칙으로 대출 가능 금액과 필요 자기자본을 계산합니다 | 2 |
| 운영 관측 | 매일 실행하는 수집과 알림 발송의 지연, 누락, 실패를 지표로 보고, 실패하면 운영자에게 알립니다 | 2 |
| 거래 변경 이벤트 분리 | 거래 변경(신규, 해제, 정정)을 이벤트로 발행하고, 집계 갱신과 알림 등이 각자 이벤트를 받아 반영합니다. 받는 쪽마다 속도와 실패 양상이 다릅니다. 알림 규칙을 바꾸면 지난 이벤트를 다시 읽어 알림 대상을 다시 계산해야 합니다 | 3 |
| collector와 알림 발송기 분리 | API 서버는 하나의 애플리케이션으로 두고, collector와 알림 발송기만 따로 실행합니다. API 서버, collector, 알림 발송기의 실패 양상과 배포 주기가 다르기 때문입니다 | 3 |
| 무중단 배포 | 수집은 예약 작업으로, API 서버는 순차 교체로 배포합니다. 배포하는 동안에도 알림을 계속 보내야 하기 때문입니다 | 3 |
| 작업 중복 실행 방지와 호출 제한 | 서버를 두 대로 실행할 때 수집 작업이 두 번 실행되지 않게 막고, 외부 API 호출 횟수를 제한합니다 | 3 |
| 서울 전체 실거래 | 실거래 수집 범위를 서울 전체 10년치로 넓힙니다 | 4 |
| 조회 성능 | 늘어난 실거래에서 단지별 추이 조회가 느려지지 않게 인덱스, 파티셔닝, 집계 테이블, 캐시 중에서 측정해 고릅니다. 부하 실험으로 응답 시간을 확인합니다 | 4 |

- 관심 단지는 임장 후보로 추가했거나, 매물을 등록했거나, 임장 기록을 남긴 단지입니다. 거래 알림과 계약 추정 표시는 관심 단지를 대상으로 합니다. 관심 단지에서 뺀 단지는 다시 추가하기 전까지 알림 대상이 아닙니다. 그 단지의 매물과 기록은 그대로 남습니다.
- 호가 출처 목록은 네이버 부동산, 호갱노노, KB부동산, 직방, 중개사무소(방문이나 전화), 기타입니다.
- 호가는 사용자가 앱이나 중개사무소에서 확인한 값을 직접 입력합니다. 캡처 인식, 매물 링크를 받아 서버가 그 페이지를 읽는 방식은 사용하지 않습니다. 서비스가 매물 호가를 자동으로 모으는 것과는 다릅니다. 자동 수집을 하지 않는다는 내용은 [하지 않을 것](#하지-않을-것)에 있습니다.
- 매물에 중개사 전화번호는 저장하지 않습니다.
- 후기 링크와 실거래 기반 시세 추정은 이번 범위에서 뺐습니다. 하지 않기로 정한 것은 아닙니다.

### 자금 계산

| 구분 | 언제 입력하나 | 항목 |
|---|---|---|
| 자금 프로필 | 처음 한 번, 바뀔 때 | 보유 현금, 앞으로 받을 돈과 받는 날짜, 각자의 연소득, 기존 대출 잔액과 연간 상환액, 보유 주택 수, 생애최초 구입 여부, 대출 조건 가정(만기, 예상 금리, 상환 방식) |
| 매물 값 | 매물마다 | 호가, KB 시세(직접 입력), 공시가격(공식 API에서 받아 참고값으로 표시), 예상 수리비와 이사비 |
| 규칙표 | 규제가 바뀔 때 직접 입력 | LTV 비율, DSR 한도, 스트레스 가산 금리, 대출 금액 상한, 취득세율, 중개보수 상한 요율. 항목마다 시행일과 출처 링크 |

- LTV는 주택 가격 대비 대출 비율, DSR은 연소득 대비 모든 대출의 연간 원리금 상환액 비율입니다.
- 대출 가능 금액은 LTV 한도, DSR 한도, 대출 금액 상한 중 가장 작은 값입니다.
- 필요 자기자본은 매매가에 취득세, 중개보수, 수리비와 이사비를 더하고 대출 가능 금액을 뺀 값입니다.
- 기준 날짜(오늘 또는 계약 예정일)에 유효한 규칙을 고릅니다. 받을 돈의 날짜를 보고 계약일과 잔금일에 돈이 모자라는지 확인합니다.
- 결과 화면에는 참고용이라는 표시를 넣고, 적용한 규칙의 시행일과 출처도 표시합니다.

## 비기능 요구사항

| 항목 | 요구사항 |
|---|---|
| 화면 | 웹 브라우저에서 동작하고, 휴대폰 세로 화면 폭에서 모든 입력과 조회를 할 수 있어야 합니다 |
| 실거래 최신성 | 신고 기한이 계약 후 30일이고 해제 신고는 더 늦게 들어올 수 있습니다. 그래서 최근 몇 달치 실거래를 매일 다시 받습니다. 다시 받는 기간은 매일 받은 결과를 비교해 정합니다(결정 기록 0009, 작성 예정) |
| 같은 거래 구분 | 매일 다시 받은 실거래에서 같은 거래를 알아보고, 해제, 정정, 등기로 바뀐 거래를 찾아야 합니다. 실거래 응답에는 거래 고유 번호와 신고일이 없고, 등기 전에는 동 정보가 비어 있습니다. 구분 방법과 바뀐 내용을 남기는 방법은 실제 데이터를 확인한 뒤 정합니다(결정 기록 0006과 0007, 작성 예정) |
| 수집 실패 격리 | 외부 API 호출이 실패하면 지역과 월 단위로 실패를 기록하고, 실패한 범위만 다시 받습니다. 한 범위가 실패해도 나머지 범위의 수집은 계속합니다 |
| 호출 한도 | 각 외부 API의 일일 호출 한도 안에서 수집합니다 |
| 알림 중복 방지 | 같은 거래나 같은 일정의 알림을 같은 사람에게 두 번 보내지 않습니다 |
| 알림 채널 교체 | 메일을 기본 채널로 둡니다. 다른 채널을 추가해도 알림 판단 로직을 고치지 않도록 발송 채널을 별도 모듈로 분리합니다 |
| 개인정보 | 소득, 자산, 부채는 민감한 개인 재무 정보입니다. 로그인 토큰과 이메일도 개인정보입니다. 컬럼마다 저장 방식(암호화 여부)을 데이터 모델에서 정합니다 |
| 지도 출처 표시 | 브이월드 지도를 사용하는 화면에 출처를 표시합니다 |

## 하지 않을 것

- 부동산 앱 화면 수집. 매물 링크를 받아 서버가 그 페이지를 읽는 방식도 화면 수집에 해당해 하지 않습니다.
- 매물 호가 수집. 서비스가 부동산 앱의 매물 호가를 자동으로 모으지 않습니다. 사용자가 출처를 골라 호가를 직접 입력하는 기능([기능 범위](#기능-범위)의 호가 직접 입력과 이력)은 여기에 해당하지 않습니다.
- KB 시세 수집. 개인이 사용할 수 있는 공식 API를 찾지 못했습니다. 자금 계산에 필요한 KB 시세는 사용자가 매물마다 직접 입력합니다. 공시가격은 공식 API로 받을 수 있지만 시세와 달라 KB 시세를 대신하지 않고 참고값으로만 표시합니다.
- 후기 저장. 블로그나 카페 후기를 서비스에 저장하지 않습니다.
- 전월세 거래. 실거래는 매매만 다룹니다.
- LLM(대규모 언어 모델) 사용. 호가 입력의 캡처 인식을 포함해 어떤 기능에도 사용하지 않습니다.

## 성공 기준

1단계를 출시한 뒤 실제 임장에 몇 주 사용해 보고 아래를 확인합니다. 수치 목표는 두지 않고, 사용하면서 불편했던 점을 기록해 다음 단계의 입력으로 씁니다.

| 기준 | 확인 방법 |
|---|---|
| 두 사용자가 방문한 매물에 각자 임장 기록을 남깁니다 | 방문 일정이 지난 매물과 임장 기록을 비교합니다 |
| 등록한 매물에 출처를 고른 호가 이력이 있습니다 | 매물 목록에서 호가 이력이 없는 매물을 찾습니다 |
| 관심 단지의 새 거래와 해제를 수집에서 발견한 날 메일로 알립니다 | 거래를 처음 발견한 시각과 메일 발송 시각을 비교합니다. 실거래 응답에 신고일이 없어 신고 시점부터 걸린 시간은 잴 수 없습니다 |
| 거래 알림이 빠지거나 두 번 오지 않습니다 | 수집한 관심 단지 거래 목록과 알림 발송 기록을 대조합니다 |
| 예약한 방문 하루 전에 알림이 옵니다 | 방문 일정과 일정 알림 발송 기록을 비교합니다 |

## 열린 질문

| 질문 | 지금까지 확인한 것 |
|---|---|
| 카카오톡 알림을 추가할지 | 1단계에는 넣지 않고 2단계 후보로 두었습니다([결정 기록 0010](adr/0010-login-method.md)). 로그인은 구글 계정으로 하므로, 카카오톡 "나에게 보내기"를 쓰려면 2단계에서 카카오 연동을 따로 검토합니다. 토큰이 만료되거나 동의를 철회하면 메일로 대신 보내야 합니다. 나와의 채팅 메시지가 휴대폰 푸시 알림으로 오는지는 아직 확인하지 않았습니다 |
| 로그인 방식 | 구글 계정의 OpenID Connect로 정했습니다([결정 기록 0010](adr/0010-login-method.md)) |
| 앱으로 옮길지와 시점 | 1단계는 웹으로 만듭니다. 앱은 실제로 써 본 뒤 정합니다 |
| 배포 환경 | 정하지 않았습니다 |
| 대출 명의 | 한 사람 명의인지 두 사람 공동 명의인지에 따라 DSR에 넣는 소득과 부채가 달라질 수 있습니다 |
| 지역 가격지수를 어느 기능에 쓸지 | 정하지 않았습니다. 출처 후보는 [한국부동산원 R-ONE Open API](https://www.reb.or.kr/r-one/portal/openapi/openApiIntroPage.do)이고 인증키 발급이 필요합니다 |
| 정책대출(디딤돌, 보금자리론 등) 자격 판단을 추가할지 | 아래 표의 기준으로 나중에 정합니다. 하지 않기로 정한 것이 아닙니다 |

| 정책대출 자격 판단 | 내용 |
|---|---|
| 지금 추가하지 않는 이유 | 상품마다 소득, 자산, 주택 가격, 가구 조건이 달라 자격 규칙이 많습니다 |
| 추가를 판단할 기준 | 보고 있는 매물 가격대가 정책대출의 주택 가격 상한 안에 드는지, 가구 소득과 자산이 자격 조건 안에 드는지 봅니다 |
| 추가할 때 필요한 것 | 자금 프로필의 가구 정보(혼인 기간, 자녀 출생일, 순자산 등)와 상품별 자격 조건, 한도 규칙이 필요합니다 |
