# 개선 후보

1단계는 애플리케이션 한 프로세스(서버 한 대)와 PostgreSQL 하나로 실행합니다([C4 컨테이너: 1단계 구성](architecture/c4-container.md#1단계-구성), [결정 기록 0005](adr/0005-modular-monolith.md)). 이 문서는 그 전제에서는 문제가 되지 않아 지금 고치지 않고, 사용자가 늘거나 서버를 여러 대로 늘릴 때 다시 볼 자리를 모읍니다. 이 항목들은 1단계 기능(백로그 001~010)을 모두 만든 뒤 [백로그 011](backlog.md#백로그)에서 측정하고 고칩니다.

- 항목의 영향과 한계는 측정하기 전의 추정입니다. 결론이 아니라 검증할 가설로 읽습니다.
- 항목마다 잴 것을 적습니다. 011에서 측정하고, 고칠지와 방법은 결정 기록에 남깁니다. 011 전에 다시 볼 계기가 먼저 오면(아래 표의 "더 일찍 볼 때") 그때 봅니다.
- Kafka, Redis, Kubernetes를 어느 단계에 어떤 조건으로 넣는지는 [결정 기록 0004](adr/0004-staged-adoption.md)가 기준입니다. 이 문서의 항목이 그 기술을 새 용도로 쓰게 되면 0004와 따로 결정 기록을 씁니다.

## 성능

| 번호 | 지금 하는 일 | 가설 | 더 일찍 볼 때 | 잴 것 | 선택지 |
|---|---|---|---|---|---|
| P1 | 로그인한 사용자의 요청마다 세션을 `spring_session`에서 읽고(SELECT 1번), 마지막 사용 시각을 고쳐 씁니다(UPDATE 1번). 유휴 7일 만료를 계산하려고 Spring Session이 하는 일입니다 | 인덱스가 걸린 행 하나를 읽고 쓰는 쿼리라 사용자 수천 명까지는 PostgreSQL 하나로 충분하다(측정 전 추정) | 실제 사용 중 화면이 느리다고 느낄 때 | 동시 사용자 수별 응답 시간, 세션 쿼리 시간, 데이터베이스 CPU와 연결 수 | P2부터 적용, 세션 저장소를 Redis로 옮김(아래 S5) |
| P2 | 절대 만료 필터(`AbsoluteExpiryFilter`)가 JS와 CSS 같은 정적 파일 요청에서도 세션을 읽어, P1의 두 쿼리가 화면을 열 때마다 파일 수만큼 더 나갑니다 | 화면 한 번에 세션 쿼리가 파일 수에 비례해 는다(코드를 읽고 판단, 실행으로 확인하지 않음) | P1과 같음 | 화면 한 번을 열 때의 세션 SELECT와 UPDATE 수 | 필터가 정적 파일 경로(`/assets/`)를 건너뜀. 화면 경로의 만료 처리는 테스트가 요구하므로 남김 |

## 서버를 여러 대로 늘리기 전에 맞출 것

앱 서버는 로그인 정보를 프로세스 메모리가 아니라 공유 데이터베이스에 두므로, 어느 서버가 요청을 받아도 같은 사용자를 알아봅니다. 같은 사용자의 로그인, 탈퇴, 표시 이름 수정은 데이터베이스의 사용자 행 잠금으로 한 줄로 서므로 서버 수와 관계없이 꼬이지 않습니다. 아래는 그래도 서버마다 따로 갖는 값이나 따로 도는 작업이라 맞춰야 하는 것입니다.

011에서 API 서버를 두 대로 실행해 아래 항목을 확인합니다. 011 전에 배포 환경을 정하며 여러 대로 실행하기로 하거나 [결정 기록 0004](adr/0004-staged-adoption.md)의 3단계 Redis 락 측정을 시작하면 그때 먼저 봅니다.

| 번호 | 자리 | 맞추지 않으면 | 할 일 |
|---|---|---|---|
| S1 | 로그인 임시 쿠키 키 `ESTATE_LOGIN_COOKIE_KEY` | 로그인 시작은 서버 A가, 구글에서 돌아오는 콜백은 서버 B가 받으면 B가 임시 쿠키를 풀지 못해 로그인이 실패함 | 모든 서버에 같은 값을 줌 |
| S2 | 열 암호화 키 `ESTATE_COLUMN_KEYS`, `ESTATE_COLUMN_KEY_ACTIVE` | 한 서버가 암호화한 로그인 이메일을 다른 서버가 복호화하지 못해 내 정보 조회가 500 | 모든 서버에 같은 값을 줌. 키를 바꿀 때는 새 버전을 모든 서버에 먼저 넣은 뒤 활성 버전을 바꿈 |
| S3 | 서버 시계 | 재인증 5분과 절대 만료 30일을 서버마다 자기 시계로 셈. 시계가 어긋나면 같은 요청의 결과가 서버마다 다름(재인증 판정은 미래 쪽 60초까지만 허용) | 모든 서버의 시계를 NTP로 맞춤 |
| S4 | 만료 세션 정리 작업 | Spring Session이 서버마다 주기적으로 만료된 세션 행을 지움. 같은 DELETE가 서버 수만큼 돎. 데이터는 틀어지지 않음 | 서버 수와 정리 쿼리 시간을 재고, 부담이 되면 한 서버에서만 돌림 |
| S5 | 세션 저장소를 Redis로 옮길 때(P1에서 필요하다고 나올 때만) | 지금은 사용자 저장, 새 세션 저장, 옛 세션 삭제가 같은 데이터베이스의 한 트랜잭션이라 중간에 실패하면 모두 되돌아감. Redis는 이 트랜잭션에 들어올 수 없어 일부만 남는 경우가 생김 | 로그인과 재인증의 저장 순서와 실패 처리, 탈퇴의 세션 삭제를 다시 설계. 재인증의 옛 세션 찾기와 탈퇴의 세션 삭제가 쓰는 `spring_session` 직접 SQL을 Spring Session의 공통 API로 바꿈. 쿠키 해시 방식은 저장소와 무관해 그대로 둠 |

## 기록 방법

- 새 후보는 같은 형식으로 표에 더합니다. 번호는 다시 쓰지 않습니다.
- 측정을 시작하면 측정 결과와 고칠지 여부를 결정 기록으로 쓰고, 해당 행의 마지막 칸 끝에 그 결정 기록 링크를 답니다.
- 고친 항목도 행을 지우지 않습니다. 링크한 결정 기록이 고친 내용을 담습니다.
