# 0013. 세션 방식

로그인은 Spring Security의 OIDC 로그인으로 하고, 브라우저에는 서버가 저장하는 세션을 HttpOnly, SameSite=Strict 쿠키로 발급하며, 데이터베이스에는 세션 ID의 해시만 저장합니다.

## 배경

- [결정 기록 0010](0010-login-method.md)은 구글 계정의 OIDC(OpenID Connect)로 로그인하기로 정했고, 로그인 뒤 세션을 쿠키 세션으로 유지할지 자체 토큰으로 유지할지와 로그인 흐름은 다음 문서로 넘겼습니다.
- [결정 기록 0012](0012-personal-data-storage.md)는 세션 토큰의 원문을 저장하지 않고 SHA-256 해시만 저장하기로 정했습니다.
- 세션을 저장하는 테이블은 [데이터 모델](../architecture/data-model.md#사용자와-가구)의 세션 저장에 있고, 이 기록의 결정에 맞춰 정합니다.
- 로그인과 세션은 Spring Security로 구현합니다. 그래서 선택지마다 Spring Security의 기본 동작과 어디가 다른지를 함께 봅니다.
- [RFC 10017](https://www.rfc-editor.org/rfc/rfc10017.html)(OAuth 2.0 for Browser-Based Applications, BCP 212, 2026-08)은 브라우저 앱의 구성 방식을 보안이 높은 순으로 나열하면서 BFF(Backend for Frontend, 서버가 토큰을 맡고 브라우저에는 쿠키만 발급하는 구조)를 첫째로 두고, 개인정보를 다루는 앱에 이 방식을 강하게 권합니다(6.1.4.3).

제약은 아래와 같습니다.

- 사용자는 두 명이고, 휴대폰 웹 브라우저로 사용합니다([PRD 사용자](../prd.md#사용자)).
- owner가 구성원을 제거하면 그 사람의 다음 요청부터 막혀야 합니다([결정 기록 0011](0011-household-sharing.md)).
- 로그아웃한 세션은 다음 요청부터 사용할 수 없어야 합니다.
- 토큰 원문은 저장하지 않습니다(결정 기록 0012).
- 서비스는 한 애플리케이션으로 실행합니다([결정 기록 0005](0005-modular-monolith.md)).

아래 표에서 XSS(스크립트 주입)는 공격자가 서비스 화면에 자기 스크립트를 실행시키는 공격이고, CSRF(Cross-Site Request Forgery, 요청 위조)는 다른 사이트가 로그인한 사용자 몰래 서비스에 요청을 보내는 공격입니다. JWT(JSON Web Token)는 사용자와 만료 시각을 담아 서명한 토큰으로, 서버가 저장하지 않고 서명만 확인합니다.

## 선택지

"쿠키냐 JWT냐"는 두 질문이 섞인 것입니다. 브라우저에 무엇을 발급하는지와, 그 값을 어디에 담아 보내는지입니다. JWT도 쿠키에 담을 수 있습니다.

| 발급하는 것 | HttpOnly 쿠키로 전송 | 화면 스크립트가 보관하다 요청 헤더로 전송 |
|---|---|---|
| 서버가 저장하는 무작위 값 | 스크립트가 값을 읽지 못하고, 서버에서 세션을 삭제하면 다음 요청부터 막힙니다 | 모바일 앱에서 흔한 방식입니다. 웹에서는 XSS가 발생하면 값이 유출됩니다 |
| JWT | 스크립트는 값을 읽지 못하지만, 서버가 만료 전에 무효화할 수 없습니다 | XSS가 발생하면 값이 유출되고, 서버도 만료 전에 무효화할 수 없습니다 |

브라우저에 주는 토큰은 아래 네 가지를 비교했습니다.

| 선택지 | 탈취된 토큰을 무효화할 수 있는지 | 구성원 제거를 바로 반영하는지 | 서버 저장소가 필요한지 | 키가 유출되면 | XSS가 발생하면 값이 유출되는지 | 선택 |
|---|---|---|---|---|---|---|
| 서버 세션과 HttpOnly 쿠키 | 무효화할 수 있습니다. 세션을 삭제하면 다음 요청부터 막힙니다 | 반영합니다. 요청마다 멤버십을 다시 읽습니다 | 필요합니다 | 세션 값은 무작위라 위조에 사용할 서명 키가 없습니다 | 유출되지 않습니다. 스크립트가 HttpOnly 쿠키를 읽지 못합니다. 다만 화면이 열려 있는 동안 주입된 스크립트가 요청을 보내는 것은 막지 못합니다 | 채택 |
| 쿠키나 헤더에 담은 긴 JWT 하나 | 만료까지 무효화하지 못합니다. 무효화하려면 차단 목록을 서버에 둬야 합니다 | 토큰에 담은 역할이 만료까지 남습니다 | 없습니다 | 서명 키가 유출되면 아무 사용자의 토큰이나 만들 수 있습니다 | 쿠키에 담으면 유출되지 않고, 헤더로 보내려고 스크립트가 보관하면 유출됩니다 | 제외. JWT의 장점인 "여러 서버가 공용 저장소 없이 서명만 보고 사용자를 식별한다"는 한 애플리케이션(결정 기록 0005)에서 사용할 곳이 없습니다. 만료 전에 무효화할 수 없다는 단점과 서명 키가 유출되면 토큰을 위조할 수 있다는 단점만 남습니다 |
| 짧은 JWT와 갱신 토큰 | JWT는 만료까지 유효합니다. 갱신 토큰은 서버에 저장해야 무효화할 수 있습니다 | JWT가 만료될 때까지 반영되지 않습니다 | 갱신 토큰 저장소가 필요합니다 | 서명 키 유출 피해는 긴 JWT와 같습니다 | 담는 곳에 따라 긴 JWT와 같습니다 | 제외. 갱신 토큰 저장소가 필요해 결국 서버가 상태를 가지면서, JWT 만료 전에는 무효화하지 못하는 단점이 남습니다 |
| 헤더로 보내는 자체 토큰 | 무효화할 수 있습니다 | 반영합니다 | 필요합니다 | 서명 키가 없습니다 | 유출됩니다. 웹 화면이 토큰을 스크립트가 읽을 수 있는 브라우저 저장소에 둡니다 | 제외. XSS가 발생하면 토큰 원문이 유출됩니다 |

세션 저장소는 아래 세 가지를 비교했습니다. [Spring Session](https://docs.spring.io/spring-session/reference/api.html)의 JDBC 저장소는 세션 ID를 `SPRING_SESSION` 테이블의 `SESSION_ID CHAR(36)` 열에 그대로 저장합니다.

| 선택지 | 내용 | 결정 기록 0012와의 관계 | 선택 |
|---|---|---|---|
| Spring Session JDBC에 해시 저장 래퍼 | 세션 수명, 만료 정리, 사용자별 세션 조회는 Spring Session에 맡기고, 세션 ID 열에는 쿠키 값의 해시만 저장하는 얇은 저장소 래퍼를 둡니다 | 지킵니다 | 채택 |
| Spring Session JDBC 기본 | 코드가 가장 적습니다 | 어긋납니다 | 제외. 세션 ID를 평문으로 저장하므로, 덤프나 백업을 탈취한 사람이 아직 유효한 세션 ID로 사용자 행세를 하고 API로 복호화된 주소와 동호수를 읽습니다. 결정 기록 0012가 암호화를 고른 전제(덤프에는 암호문만 보인다)가 무너집니다 |
| 직접 만든 세션 테이블 | 토큰 해시를 저장하는 테이블을 직접 둡니다 | 지킵니다 | 제외. Spring Security와 연동하는 부분(로그인 정보 저장, 만료 정리)을 모두 직접 만들어야 합니다 |

세션 쿠키의 SameSite 속성은 아래 두 가지를 비교했습니다. SameSite는 브라우저가 다른 사이트에서 시작한 요청에 쿠키를 전송할지 정하는 속성입니다.

| 선택지 | 내용 | 선택 |
|---|---|---|
| Strict | 다른 사이트에서 시작한 화면 이동(메일의 링크, 구글에서 돌아오는 콜백)에는 세션 쿠키가 전송되지 않고, 그 뒤 화면이 서비스 주소로 보내는 요청에는 전송됩니다. RFC 10017 6.1.3.2가 권합니다 | 채택 |
| Lax | Spring Security 기본대로 로그인 임시 값을 서버 세션에 둘 수 있어 구현이 가장 단순합니다 | 제외. 다른 사이트에서 시작한 화면 이동에 세션 쿠키가 전송되므로, 요청 위조 방어로 Origin 검사와 "GET은 상태를 바꾸지 않음" 규칙만 남습니다 |

## 결정

로그인은 [Spring Security](https://docs.spring.io/spring-security/reference/servlet/oauth2/client/authorization-grants.html)의 OAuth2 로그인(`oauth2Login`, OIDC)으로 하고, 브라우저에는 JWT를 발급하지 않고 서버가 저장하는 세션을 쿠키로 발급합니다(RFC 10017의 BFF 방식).

세션은 아래와 같이 다룹니다.

- 로그인하면 32바이트 무작위 토큰을 세션 ID로 만들어 쿠키로 발급합니다. 쿠키의 원문 토큰은 이 32바이트를 패딩 없는 base64url(43자)로 바꾼 값입니다. 인증할 때마다 세션 ID를 새로 만들어, 로그인 전에 공격자가 심어 둔 세션 ID가 로그인 뒤에도 사용되는 공격(세션 고정)을 막습니다.
- 로그인을 마치면 구글이 준 ID 토큰, 액세스 토큰, 그 안의 이메일 같은 클레임을 세션에 저장하지 않습니다. Spring Security의 기본 로그인 정보는 주체(`DefaultOidcUser`)와 권한 목록 둘 다에 ID 토큰과 사용자 정보를 담습니다. 권한 목록에도 `OidcUserAuthority`가 저장되고, 이 객체가 ID 토큰과 사용자 정보(이메일 포함)를 담기 때문입니다. 그래서 주체와 권한 목록을 둘 다 바꿔, 세션에는 서비스 사용자 번호(`user.id`)와 ID 토큰의 `auth_time`만 담은 로그인 정보를 저장합니다. 역할은 세션에 없고 요청마다 멤버십에서 읽습니다. 이 Spring Security 동작은 버전에 따라 다를 수 있어 구현 때 확인합니다. 인가된 클라이언트(액세스 토큰)도 보관하지 않습니다(결정 기록 0012의 "구글 토큰은 저장하지 않는다").
- 세션은 Spring Session JDBC에 저장하고, `session_id` 열에는 토큰의 SHA-256 해시만 저장하는 저장소 래퍼를 둡니다. 기본 스키마의 `SESSION_ID CHAR(36)`은 해시 길이에 맞게 넓힙니다. 사용자별 세션 조회 키(`principal_name`)에는 `user.id`를 넣습니다. 3단계에서 Redis를 넣으면 같은 구조로 저장소를 바꿉니다([결정 기록 0004](0004-staged-adoption.md)).
- 토큰 원문은 쿠키와 발급하는 순간에만 있습니다. 쿠키를 읽는 경계(세션 ID를 꺼내는 곳)에서 한 번만 해시하고, 그 안쪽의 모든 저장소 연산(조회, 저장, 세션 ID 변경, 로그아웃 삭제, `principal_name`으로 찾은 뒤 하는 탈퇴 삭제, 콜백의 옛 세션 삭제)은 해시 값만 다룹니다. 세션 ID를 바꿀 때는 새 원문 토큰을 만들어 쿠키로 발급하고 그 해시를 저장합니다. `principal_name`으로 찾은 행은 저장된 값으로 바로 삭제하고, 다시 해시하지 않습니다. 콜백의 옛 세션 참조도 임시 값 쿠키에 담긴 이미 저장된 해시이므로 그대로 삭제에 사용하고 다시 해시하지 않습니다. 콜백의 옛 세션 참조에서는 로그인 시작 요청이 세션 쿠키를 읽어 해시한 것이 그 "한 번"입니다.
- 세션은 7일 동안 요청이 없으면 만료되고(유휴 만료), 계속 사용해도 로그인한 지 30일이 지나면 만료됩니다(절대 만료). 만료되면 다시 로그인합니다.
- 로그인할 때마다 새 세션을 만듭니다. 같은 사용자가 휴대폰과 컴퓨터처럼 여러 곳에서 로그인하면 세션이 여럿 생깁니다.
  - Strict 세션 쿠키는 구글에서 돌아오는 콜백 요청에 전송되지 않으므로, 콜백은 옛 세션을 직접 볼 수 없습니다. 그래서 옛 세션 참조를 로그인 시작 요청에서 임시 값 쿠키로 넘깁니다. 로그인 시작 요청은 서비스 화면에서 누르는 같은 사이트 이동이라 세션 쿠키가 전송됩니다. 세션 쿠키가 있으면 그 세션의 저장된 세션 ID(해시)와 목적(일반 로그인 또는 재인증)과 시작 시각을 임시 값 쿠키에 함께 담습니다.
  - 콜백 요청은 state와 ID 토큰을 확인합니다. 일반 로그인이거나 재인증의 세 조건(아래 재인증 불릿)을 모두 통과했을 때 새 세션(새 무작위 토큰, 새 행)을 발급하고, 임시 값 쿠키에 옛 세션 참조가 있으면 그 행을 삭제합니다. 재인증 실패에는 새 세션이 없습니다.
  - 새 세션 행 저장과 옛 세션 행 삭제는 한 데이터베이스 트랜잭션으로 커밋합니다. 둘 중 하나라도 실패하면 둘 다 롤백하고, 새 세션 쿠키를 발급하지 않은 채 로그인 실패를 알리는 화면으로 보냅니다. 사용자는 로그인을 다시 시작합니다. 화면과 문구는 기능 명세에서 정합니다.
  - 일반 로그인에서는 옛 세션 행이 이미 없어 삭제된 행이 없어도 성공으로 봅니다.
  - 재인증에서는 `sub`와 `auth_time` 조건을 통과하면 셋째 조건(옛 세션의 존재와 만료 전) 확인과 옛 세션 행 삭제를 새 세션 저장과 같은 트랜잭션에서 합니다. 삭제된 행이 정확히 하나가 아니면 둘 다 롤백하고 재인증 실패로 처리합니다. `sub` 불일치 때의 옛 세션 삭제는 새 세션 저장과 묶지 않고 따로 커밋하며, 재인증 실패 처리로 롤백하지 않습니다.
  - 다른 사이트에서 시작된 로그인 시작 요청에는 Strict 세션 쿠키가 전송되지 않아 참조가 없으므로, 다른 사이트의 링크로 사용자의 세션을 삭제할 수 없습니다.
- 로그아웃하면 그 기기의 세션만 삭제합니다. 탈퇴하면 그 사용자의 세션을 모두 삭제합니다.
- 역할은 세션에 담지 않고, 요청마다 멤버십(`household_member`)을 다시 읽어 권한 키를 확인합니다. 그래서 owner가 구성원을 제거하면 그 사람의 세션이 남아 있어도 다음 요청부터 가구의 자원에 접근하지 못합니다.

쿠키는 두 개입니다.

| 쿠키 | 담는 것 | 속성 | 이유 |
|---|---|---|---|
| `__Host-Http-session` | 세션 토큰 | HttpOnly, Secure, SameSite=Strict, Path=/, Domain 없음. 수명은 위 세션 수명을 따릅니다 | RFC 10017 6.1.3.2가 권하는 속성과 이름 접두사입니다. `__Host-` 접두사가 붙은 쿠키는 브라우저가 Secure와 Path=/가 있고 Domain 속성이 없을 때만 받으므로, 하위 도메인이 같은 이름의 쿠키를 만들지 못합니다. `Http` 부분은 스크립트가 아니라 서버 응답 헤더로만 이 이름의 쿠키를 만들 수 있게 하는 표시이고, 브라우저 지원은 구현 때 확인합니다 |
| `__Host-Http-login` | 로그인 임시 값(state, nonce, PKCE 검증값, 돌아갈 경로, 옛 세션 참조, 목적, 시작 시각) | 10분, HttpOnly, Secure, SameSite=Lax, Path=/. 값은 위조를 감지하는 인증 암호화(결정 기록 0012의 AES-GCM과 같은 방식)를 적용합니다 | 콜백 요청은 구글에서 서비스로 돌아오는 최상위 화면 이동이라, Strict 쿠키는 콜백에 전송되지 않습니다. 그래서 Spring Security가 기본으로 서버 세션에 두는 로그인 요청 저장소를 이 쿠키 방식으로 바꿉니다. 임시 값은 데이터베이스에 저장하지 않습니다 |

웹 화면은 처음 받는 HTML에 개인 자료를 담지 않고, 자료는 화면이 서비스 주소로 보내는 API 요청으로 받습니다. 그래서 메일 링크로 들어와 첫 화면 이동에 Strict 쿠키가 전송되지 않아도, 첫 API 요청부터 쿠키가 전송됩니다.

요청 위조는 세 가지로 막습니다.

- 세션 쿠키의 SameSite=Strict는 다른 사이트에서 시작한 요청에 세션 쿠키를 전송하지 않습니다.
- 상태를 바꾸는 요청은 Origin 헤더가 서비스 주소와 같은지 검사합니다. Origin 헤더가 없으면 Referer 헤더의 주소로 확인하고, 둘 다 없으면 요청을 거부합니다.
- [API 공통 규칙](../architecture/api-conventions.md#경로와-형식)의 안전한 메서드 규칙에 따라 GET 요청은 상태를 바꾸지 않습니다.

로그인 시작 요청과 콜백 요청은 Origin 검사와 안전한 메서드 규칙의 예외입니다. 콜백은 구글에서 돌아오는 최상위 GET 이동이라 Origin이 서비스 주소와 다르거나 비어 있고, 세션을 만드는 일을 GET에서 할 수밖에 없기 때문입니다. 로그인 시작 요청은 세션을 바꾸지 않고 임시 값 쿠키만 새로 만듭니다. 그래서 다른 사이트가 이 요청을 시작시켜도 일어나는 일은 둘뿐입니다. 진행 중이던 로그인이 처음부터 다시 시작되거나, 이 브라우저가 구글에 로그인해 있고 이미 동의한 상태라면 그 구글 계정(사용자 본인의 계정)의 새 세션으로 바뀝니다. 공격자의 계정으로는 바뀌지 않습니다. 콜백의 state가 이 브라우저의 임시 값 쿠키와 같아야 하므로, 공격자가 자기 계정으로 받은 인가 코드를 사용할 수 없기 때문입니다. 위조된 콜백은 아래 로그인 흐름의 state, nonce, PKCE 검증값으로 막습니다. 다른 사이트에서 시작된 로그인은 옛 세션 참조가 없어 옛 행을 삭제하지 않으므로, 구글이 동의 화면을 건너뛰는 상태라면 사용되지 않는 세션 행이 늘어날 수 있고, 이런 행은 유휴 7일 뒤 정리됩니다.

웹 화면과 API를 같은 주소에 두고, API는 경로로 구분합니다. 위 쿠키 설정은 이 전제에서만 맞습니다. 배포 환경은 [PRD 열린 질문](../prd.md#열린-질문)에 남아 있으므로, 두 주소가 나뉘면 쿠키 설정을 재검토합니다.

로그인 흐름은 Authorization Code 방식에 PKCE(Proof Key for Code Exchange, 인가 코드를 가로챈 사람이 토큰으로 바꾸지 못하게 하는 검증값)를 S256으로 추가해 사용합니다. API 서버가 OAuth 클라이언트가 되어 클라이언트 비밀값을 가집니다. Spring Security는 비밀값을 가진 클라이언트에 PKCE를 자동으로 활성화하지 않으므로 `requireProofKey=true`로 활성화합니다. 로그인 시작과 콜백은 엔드포인트 경로 대신 역할 이름(로그인 시작 요청, 콜백 요청)으로 적습니다.

- 로그인 시작 요청에서 state, nonce, PKCE 검증값, 돌아갈 경로를 만들고, 세션 쿠키가 있으면 옛 세션 참조(저장된 세션 ID 해시), 목적, 시작 시각을 추가해 `__Host-Http-login` 쿠키에 담고 구글 로그인 화면으로 보냅니다.
- 콜백 요청에서 state를 쿠키의 값과 비교하고, 비교한 뒤 임시 값 쿠키를 삭제합니다. state를 비교하지 않으면 공격자가 자기 계정의 인가 코드로 사용자를 공격자 계정에 로그인시킬 수 있습니다.
- 리다이렉트 주소는 구글 콘솔에 등록한 콜백 주소 하나와 정확히 같아야 합니다.
- 인가 코드와 PKCE 검증값으로 받은 ID 토큰은 아래 항목을 모두 확인한 뒤에만 받아들입니다. Spring Security의 OIDC 로그인이 확인하는 항목이고, 이 표는 그 설정이 맞춰야 할 조건입니다. 사용자는 `sub`로 찾습니다.

| 확인 항목 | 조건 | 이유 |
|---|---|---|
| 서명 | 구글 공개키로 확인하고, 알고리즘은 RS256만 허용합니다 | 허용 알고리즘을 고정하지 않으면 토큰 머리에 적힌 알고리즘을 바꿔 서명 확인을 피하는 공격을 받습니다 |
| `iss` | `https://accounts.google.com` 또는 `accounts.google.com`(구글이 사용하는 두 값) | 다른 발급자가 만든 토큰을 받지 않습니다 |
| `aud` | 우리 클라이언트 ID | 확인하지 않으면 서명만 맞는 다른 앱용 구글 토큰을 받아들입니다 |
| `exp` | 현재 시각 전이 아님 | 만료된 토큰을 받지 않습니다 |
| `nonce` | 임시 값 쿠키의 nonce와 같음 | 이전 로그인에서 나온 ID 토큰을 다시 사용하지 못하게 합니다 |
| `auth_time` | 재인증 요청(`max_age`를 보냄)에서는 있어야 합니다. OIDC 표준은 이때 `auth_time`을 반환하라고 정하지만, 구글이 실제로 따르는지는 구현 때 확인합니다. 값(초 단위)은 임시 값 쿠키에 초 단위로 담은 재인증 시작 시각과 비교해, 시작 시각보다 60초를 넘게 앞서면 실패입니다. 서버의 현재 시각보다 60초를 넘게 뒤(미래)여도 실패입니다. 60초는 서버와 구글의 시계 오차를 허용하는 폭입니다 | 구글에서 실제로 인증한 시각이 아닌 예전 인증 결과를 재인증으로 받아들이지 않습니다 |

- 돌아갈 경로는 아래 조건을 모두 만족하는 서비스 안 경로만 받습니다. 그 밖의 값이면 `/`로 보냅니다.
  - `/`로 시작합니다.
  - `//`나 `/\`로 시작하지 않습니다.
  - 제어 문자(탭, 줄바꿈 등)와 역슬래시(`\`)를 하나도 포함하지 않습니다.

  브라우저는 주소를 해석할 때 탭과 줄바꿈을 제거하므로 `/` 다음에 탭을 넣은 값이 `//`로 시작하는 다른 사이트 주소가 될 수 있고, 줄바꿈은 응답 헤더에 다른 줄을 추가하는 데 사용될 수 있습니다. 역슬래시도 거부하는 이유는 브라우저가 주소의 역슬래시를 슬래시처럼 해석해 `/\` 같은 값이 `//`로 시작하는 다른 사이트 주소가 될 수 있기 때문입니다. 검사는 퍼센트 인코딩(`%09` 같은)을 푼 값에 하고, 리다이렉트 응답의 Location에 사용하는 값과 같은 값을 검사합니다.
- 첫 로그인 때 사용자 행(`user`)과 알림 설정 행(`notification_setting`)을 만듭니다. 알림 설정 행의 `trade_alert_on_at`에는 첫 로그인 시각을 적고(거래 알림 켬), `visit_alert_on`은 참, `visit_alert_lead_hours`는 24(하루 전)로 둡니다. 가구는 만들지 않습니다. 멤버십이 없는 사용자는 가구 없음 화면에서 직접 가구를 만들거나 초대 링크로 들어옵니다([데이터 모델 `household`](../architecture/data-model.md#household)).

탈취된 세션으로 할 수 있는 일을 줄이려고 아래 둘을 추가합니다.

- 민감 동작 넷(가구 삭제, 구성원 제거, 탈퇴, 초대 발급)은 구글 재인증을 거칩니다. 알림 켜고 끄기는 재인증 대상이 아닙니다.
  - 마지막 인증 시각은 콜백 시각이 아니라 ID 토큰의 `auth_time`(구글이 사용자를 실제로 인증한 시각)이고, 세션에 이 값을 둡니다. `auth_time`이 없으면 오래된 것으로 보고 민감 동작에 재인증을 요구합니다.
  - 민감 동작의 5분 판정은 서버의 현재 시각과 세션에 둔 `auth_time`의 차이를 초 단위로 계산해 합니다. 이 차이가 5분보다 크면 재인증이 필요하다는 오류를 응답합니다.
  - `auth_time`이 서버의 현재 시각보다 60초를 넘게 미래이면 오래된 것으로 보고 같은 오류를 응답합니다. 60초는 재인증 콜백과 같은 시계 오차 허용 폭입니다.
  - 웹 화면은 구글 로그인을 `max_age=0`(구글에 사용자 인증을 다시 하라고 요청하는 값)으로 다시 거칩니다. 로그인과 재인증은 사용자가 화면에서 버튼을 눌렀을 때만 시작하고, 화면을 열 때 자동으로 시작하지 않습니다.
  - 재인증을 마치고 돌아오면 웹 화면은 밀린 민감 동작을 자동으로 다시 보내지 않고, 사용자가 같은 버튼을 다시 누릅니다. 밀린 동작과 입력값은 브라우저 저장소, 주소(URL), 돌아갈 경로 어디에도 담지 않습니다. 다른 사이트의 링크로 연 화면이 재인증과 민감 동작을 이어서 실행하지 못하게 하려는 것입니다.
- 재인증 목적의 콜백은 아래 세 조건을 모두 확인합니다.
  1. ID 토큰의 `sub`가 옛 세션 사용자의 `provider_subject`와 같습니다.
  2. `auth_time`이 임시 값 쿠키에 초 단위로 담은 재인증 시작 시각과 초 단위로 비교해 시작 시각보다 60초를 넘게 앞서지 않으며, 서버의 현재 시각보다 60초를 넘게 뒤가 아닙니다.
  3. 참조한 옛 세션이 콜백 시각에 아직 있고 유휴 만료와 절대 만료 전입니다.

  `sub` 확인은 다른 구글 계정으로 재인증해 민감 동작 제한을 넘는 길을 막으려는 것입니다. 하나라도 아니면 재인증 실패입니다. 콜백은 최상위 화면 이동이므로, 새 세션을 발급하지 않은 채 재인증 실패를 알리는 화면으로 보냅니다. 화면과 문구는 기능 명세에서 정합니다. `sub`가 다르면 옛 세션도 삭제합니다. 쿠키를 탈취한 사람이 자기 구글 계정으로 재인증을 시도한 신호로 보기 때문이고, 실수로 다른 계정(예: 가족 계정)을 고른 본인은 다시 로그인하면 됩니다. `sub`가 같고 나머지 두 조건 가운데 하나로 실패하면 옛 세션을 그대로 둡니다. 재인증에 성공하면 새 세션이 발급되므로 절대 30일은 재인증 시각부터 다시 셉니다. 재인증은 구글이 다시 인증하게 한 인증이기 때문입니다. `max_age`를 보내면 구글이 인증을 다시 거치게 하고 `auth_time`을 반환한다는 것은 OIDC 표준이 정한 동작이며, 구글이 실제로 그렇게 동작하는지는 구현 때 확인합니다.
- 응답 헤더에 HSTS(HTTP Strict Transport Security, 브라우저가 이 서비스에 늘 HTTPS로만 접속하게 하는 헤더)와 CSP(Content Security Policy, 허용한 출처의 스크립트만 실행하게 하는 헤더)를 둡니다. 지도 API처럼 웹 화면이 직접 호출하는 외부 주소는 CSP 허용 목록에 넣고, 정확한 값은 구현에서 정합니다.

세션이 탈취되는 경로마다 막는 것과 남는 위험은 아래와 같습니다.

| 경로 | 공격자가 얻는 것 | 막는 것 | 남는 위험 |
|---|---|---|---|
| 네트워크 가로채기 | 세션 쿠키 | Secure 쿠키라 HTTPS로만 보냅니다. HSTS로 브라우저가 HTTP로 접속하지 않습니다 | 브라우저가 HSTS 헤더를 처음 받기 전의 첫 접속 |
| 화면 XSS | 쿠키 값은 얻지 못합니다. 화면이 열린 동안 사용자 행세는 할 수 있습니다 | HttpOnly 쿠키, CSP, 민감 동작 재인증 | 화면이 열린 동안 민감 동작이 아닌 요청(기록 읽기와 쓰기)을 대신 보냅니다. 사용자가 구글 인증(로그인이나 재인증)을 마친 뒤 5분 안이면 민감 동작도 대신 보낼 수 있습니다 |
| 기기나 브라우저 탈취(악성 확장, 쿠키 파일 복사, 공용 PC) | 세션 쿠키 원본 | 유휴 7일과 절대 30일 만료, 민감 동작 재인증, 재인증 때 다른 구글 계정이면 세션 삭제 | 유휴 7일과 절대 30일 안에서 사용자 행세를 할 수 있습니다. 민감 동작은 재인증에서 막힙니다. 다만 사용자가 구글 인증을 마친 뒤 5분 안에 쿠키가 탈취되면 그 5분 동안은 민감 동작도 통과합니다. 재인증 대상이 아닌 동작으로 비슷한 결과를 낼 수 있습니다. 매물과 기록을 하나씩 삭제하거나 알림을 꺼 둘 수 있습니다. 사용자가 이를 알아챌 수단이 없고, 다른 기기의 세션을 무효화하는 수단은 탈퇴뿐입니다. 로그인한 기기 목록과 기기별 로그아웃은 2단계 후보입니다 |
| 데이터베이스 덤프나 백업 유출 | 세션 저장소의 값 | 세션 ID 열에는 해시만 있어 쿠키 값을 되살릴 수 없습니다 | 세션 속성의 로그인 정보(서비스 사용자 번호와 `auth_time`)는 보입니다. 다른 개인정보 열은 결정 기록 0012가 다룹니다 |
| 로그 유출 | 로그에 남은 쿠키나 토큰 | 토큰 원문을 로그에 남기지 않습니다(결정 기록 0012) | 프록시나 웹 서버의 접근 로그가 요청 헤더를 기록하면 쿠키가 남습니다 |
| 다른 사이트에서 시작된 로그인 | 없음 | 로그인 시작 요청은 임시 값 쿠키만 새로 만들고, state를 이 브라우저의 쿠키와 비교합니다 | 옛 세션 참조가 없어 옛 행을 삭제하지 않으므로, 구글이 동의 화면을 건너뛰는 상태라면 사용되지 않는 세션 행이 늘어날 수 있습니다. 유휴 7일 뒤 정리됩니다 |
| 구글 계정 탈취 | 새 로그인 | 이 서비스의 범위 밖입니다 | 공격자가 새 세션을 만들고, 구글 재인증도 통과합니다 |

## 결과

- [데이터 모델](../architecture/data-model.md#사용자와-가구)의 세션 저장이 Spring Session 테이블 둘(`spring_session`, `spring_session_attributes`)로 바뀝니다. 세션 속성에는 위 결정의 최소 로그인 정보만 저장됩니다.
- [결정 기록 0012](0012-personal-data-storage.md)의 세션 토큰 해시 설명이 Spring Session의 세션 ID 열에 해시를 저장하는 방식으로 바뀝니다.
- 기능마다 `/speckit-plan`이 만드는 계약(`contracts/`)은 [API 공통 규칙](../architecture/api-conventions.md#기능의-계약-파일)을 따릅니다. 민감 동작의 재인증 표기와 세션 쿠키 이름도 그 규칙에 맞춥니다([인증과 권한 확인](../architecture/api-conventions.md#인증과-권한-확인)).
- 구글이 `max_age`를 따르지 않거나 `auth_time`을 주지 않으면 재인증이 늘 실패해 민감 동작을 사용할 수 없습니다. 반대로 구글이 인증을 다시 거치지 않고 `auth_time`을 토큰 발급 시각으로 주면 재인증이 실제 인증 없이 통과합니다. 구현 때 두 경우를 모두 확인하고, 어느 쪽이든 해당하면 이 결정을 재검토합니다.
- 로그인한 기기 목록과 기기별 로그아웃은 2단계 후보로 둡니다. 사용자별 세션 조회 키(`principal_name`)가 있으므로 저장소는 바꾸지 않아도 됩니다.
- 임시 값 쿠키의 암호화 키는 결정 기록 0012의 키처럼 데이터베이스 밖에 둡니다.
- 구현 때 확인합니다. Spring Security의 기본 요청 캐시는 로그인 전에 세션을 만들므로 끕니다. 돌아갈 경로는 임시 값 쿠키에 있습니다.
- 구현 때 정합니다. 화면을 다른 사이트에 겹쳐 넣지 못하게 하는 CSP의 `frame-ancestors` 값을 정합니다.
- 배포 환경을 정할 때 웹 화면과 API를 같은 주소에 두는 전제를 다시 확인합니다.
- 앱을 만들면 헤더로 보내는 자체 토큰을 재검토합니다.
