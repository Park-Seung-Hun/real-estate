# 0005. 하나의 애플리케이션으로 두는 부분과 따로 실행하는 부분

API 서버는 하나의 애플리케이션으로 두고, collector와 알림 발송기는 1단계와 2단계에는 같은 애플리케이션의 모듈로 실행하다가 3단계부터 따로 실행합니다.

## 배경

서비스 안에는 하는 일이 다른 구성 요소 세 개가 있습니다.

| 구성 요소 | 하는 일 | 관련된 PRD 요구사항 |
|---|---|---|
| API 서버 | 화면이 호출하는 API에 응답합니다 | 배포하는 동안에도 알림을 계속 보내야 하므로, API 서버를 배포할 때 알림 발송이 함께 멈추면 안 됩니다(무중단 배포) |
| collector | 외부 API에서 실거래를 매일 받고 바뀐 거래를 찾습니다 | 한 범위가 실패해도 나머지 범위의 수집은 계속하고, 실패한 범위만 다시 받습니다(수집 실패 격리). 각 외부 API의 하루 호출 한도 안에서 수집합니다(호출 한도) |
| 알림 발송기 | 알림 대상을 정하고 메일 발송 서비스로 알림을 보냅니다 | 같은 거래나 같은 일정의 알림을 같은 사람에게 두 번 보내지 않습니다(알림 중복 방지) |

- 괄호 안은 [PRD 기능 범위](../prd.md#기능-범위)와 [비기능 요구사항](../prd.md#비기능-요구사항)의 행 이름입니다.
- PRD는 3단계 기능 "collector와 알림 발송기 분리"에서, 세 구성 요소의 실패 양상과 배포 주기가 다르다는 이유로 API 서버는 하나의 애플리케이션으로 두고 collector와 알림 발송기만 따로 실행하기로 했습니다. 이 기록은 그 분리를 언제 하고 1단계를 어떤 구조로 시작할지 정합니다.
- 1단계는 사용자 두 명과 관심 지역(한 자치구)의 실거래만 다룹니다. 무중단 배포와 서버 두 대 실행은 3단계 기능입니다.

## 선택지

| 선택지 | 내용 | 선택 |
|---|---|---|
| 계속 하나의 애플리케이션 | 3단계부터도 세 구성 요소를 한 애플리케이션에서 실행합니다 | 선택하지 않음. API 서버를 배포할 때마다 collector와 알림 발송기도 다시 시작됩니다. 한 구성 요소의 실패로 프로세스가 멈추면 나머지도 함께 멈춥니다 |
| 1단계는 하나의 애플리케이션, 3단계부터 collector와 알림 발송기를 따로 실행 | 1단계와 2단계에는 세 구성 요소를 한 애플리케이션 안의 모듈로 실행하고, 3단계에 collector와 알림 발송기를 따로 실행합니다 | 채택 |
| 1단계부터 셋을 따로 실행 | 세 구성 요소를 1단계부터 각각 실행합니다 | 선택하지 않음. 1단계 기능을 출시하기 전에 실행 단위 세 개의 배포와 실행 설정을 갖춰야 합니다. 나누는 이유인 무중단 배포는 3단계 기능입니다 |
| API 서버도 기능별로 나눠 실행 | 매물, 임장 기록, 실거래 조회 같은 화면 기능을 각각 따로 실행합니다 | 선택하지 않음. PRD는 API 서버를 하나의 애플리케이션으로 두기로 했습니다. 이 기능들은 모두 사용자 요청에 응답하고, 호가와 실거래 비교처럼 매물과 실거래를 함께 읽습니다 |

## 결정

- API 서버는 하나의 애플리케이션(Java, Spring Boot)으로 둡니다. 로그인과 가족 공유, 매물, 호가 이력, 임장 기록, 실거래 조회와 2단계에 더하는 화면 기능을 기능별로 나눠 실행하지 않습니다.
- collector와 알림 발송기는 API 서버와 따로 실행합니다. 1단계와 2단계에는 세 구성 요소가 하나의 애플리케이션 안에서 모듈로 실행되고, 3단계부터 collector와 알림 발송기를 따로 실행합니다.
- 3단계에 따로 실행하려면 1단계부터 세 모듈의 경계가 나뉘어 있어야 합니다. 한 애플리케이션 안을 모듈 경계로 나눈 이 구조를 모듈러 모놀리스(modular monolith)라고 부릅니다.

collector와 알림 발송기를 따로 실행하는 이유는 아래와 같습니다.

- collector는 외부 API 호출이 실패하면 실패한 범위만 다시 받아야 하고(수집 실패 격리), 알림 발송기는 메일 발송 서비스를 호출하면서 같은 알림을 두 번 보내지 않아야 합니다(알림 중복 방지). 둘 다 외부 서비스의 실패를 다루므로 실패 양상이 API 서버와 다릅니다. 프로세스를 나누면 한쪽 프로세스가 멈춰도 다른 쪽은 계속 실행됩니다.
- API 서버를 순차 교체로 배포하는 동안에도 알림 발송기는 계속 실행되어 알림을 보냅니다(무중단 배포).
- collector나 알림 발송기만 고쳤을 때 API 서버를 다시 시작하지 않고 배포합니다. API 서버만 고쳤을 때도 마찬가지입니다.

1단계에 나누지 않는 이유는 무중단 배포와 서버 두 대 실행이 3단계 기능이기 때문입니다. 실행 단위가 하나면 1단계에는 배포와 실행 설정도 하나만 준비합니다.

## 결과

- [C4 컨테이너](../architecture/c4-container.md)의 1단계 다이어그램은 세 모듈을 애플리케이션 하나 안에 그리고, 목표 다이어그램은 셋을 따로 그립니다.
- 1단계와 2단계에는 애플리케이션이 멈추면 수집과 알림을 포함한 모든 기능이 함께 멈춥니다.
- C4 컴포넌트(`docs/architecture/c4-component.md`, 작성 예정)는 3단계에 collector와 알림 발송기를 따로 실행한다는 전제로 1단계 모듈 경계와 모듈 사이 전달 방식을 정합니다.
- 3단계에서 거래 변경 이벤트를 받는 쪽 중 집계 갱신은 API 서버 애플리케이션에 둡니다. PRD가 따로 실행하는 구성 요소를 collector와 알림 발송기로 한정했고, 집계 결과를 읽는 실거래 추이 조회가 API 서버에 있기 때문입니다.
- 따로 실행한 뒤의 배포 방식(Kubernetes), 수집 작업 중복 실행 방지(Redis), 거래 변경 전달(Kafka)은 [결정 기록 0004](0004-staged-adoption.md)의 도입 조건을 측정해 정합니다.
- 3단계에서 데이터베이스를 구성 요소마다 나눌지는 정하지 않았습니다. C4 컨테이너의 목표 다이어그램은 PostgreSQL 하나로 그렸습니다.
