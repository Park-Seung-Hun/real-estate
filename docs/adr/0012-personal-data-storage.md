# 0012. 개인정보 저장 방식

이메일, 매물 주소, 동과 호는 애플리케이션이 AES-GCM으로 암호화해 저장하고, 세션 토큰과 초대 토큰은 해시만 저장합니다. 구글이 준 토큰은 저장하지 않고 서버 세션에도 저장하지 않습니다.

## 배경

- [PRD 비기능 요구사항](../prd.md#비기능-요구사항)의 개인정보 항목은 로그인 토큰과 이메일을 개인정보로 보고, 컬럼마다 저장 방식을 데이터 모델에서 정하라고 합니다. [결정 기록 0010](0010-login-method.md)의 결과 절도 로그인 토큰과 이메일의 저장 방식을 데이터 모델로 넘겼습니다.
- 1단계 테이블에서 개인정보가 담기는 열은 아래와 같습니다. 표의 저장 방식 칸이 열마다 방식을 적습니다. 테이블 전체는 [데이터 모델](../architecture/data-model.md)에 있습니다.

| 열 | 담는 것 | 저장 방식 |
|---|---|---|
| `user.login_email` | 구글 계정 이메일 | 암호화 |
| `listing.address`, `listing.dong`, `listing.ho` | 가족이 보러 다니는 매물의 주소와 동호수 | 암호화 |
| `user.display_name` | 구글 프로필 이름(보통 실명)에서 시작하는 표시 이름 | 평문 |
| `spring_session.session_id`, `invitation.token_hash` | 로그인 세션 토큰(Spring Session 세션 테이블의 세션 ID 열)과 가족 초대 링크 토큰 | 해시 |

구글 subject(`user.provider_subject`)는 구글이 계정마다 주는 식별자라 그 자체로 사람을 식별할 수 없어 평문으로 둡니다. 임장 메모(`visit_log.memo`)는 사용자가 작성하는 자유 입력이라 개인정보가 담길 수 있지만 집을 평가한 내용이라 암호화 대상에 넣지 않습니다.

- 이 기록은 1단계 테이블만 다룹니다. 2단계 자금 프로필의 소득, 자산, 부채는 그 테이블을 설계할 때 정합니다.

## 선택지

| 선택지 | 내용 | 막는 것 | 막지 못하는 것 | 선택 |
|---|---|---|---|---|
| 암호화 안 함 | 평문으로 저장하고 데이터베이스 접근 권한만 제한합니다 | 없습니다 | 백업 파일, 덤프, 디스크가 유출되거나 데이터베이스 계정이 탈취되면 모든 값이 평문으로 보입니다 | 제외 |
| 데이터베이스 수준 암호화 | 디스크나 테이블스페이스 전체를 암호화합니다 | 디스크나 백업 매체만 가져간 경우 | 데이터베이스에 접속해 조회하면 평문이 보입니다. 데이터베이스 계정이 탈취된 경우와 덤프는 막지 못합니다 | 제외 |
| 애플리케이션 계층 열 암호화 | 애플리케이션이 값을 암호화한 뒤 저장하고, 키는 데이터베이스 밖에 둡니다 | 백업 파일, 덤프, 데이터베이스 계정으로 직접 조회한 결과에 암호문만 보입니다 | 애플리케이션 서버와 키가 함께 탈취된 경우, 내부자가 정상 경로(서비스 화면이나 API)로 읽는 경우 | 채택 |

애플리케이션 계층 열 암호화를 사용하면 암호화한 열은 데이터베이스에서 값으로 찾거나 정렬할 수 없습니다. 화면에는 주소, 동, 호로 찾는 기능이 없고([와이어프레임](../design/wireframes.md)), 같은 사용자는 제공자와 subject로 찾으므로([결정 기록 0010](0010-login-method.md)) 이메일로 찾을 일도 없습니다.

## 결정

- 암호화하는 값은 세 종류(열 네 개)입니다. 로그인 이메일(`user.login_email`), 매물 주소(`listing.address`), 동과 호(`listing.dong`, `listing.ho`)를 애플리케이션 계층에서 AES-GCM으로 암호화해 bytea 열에 저장합니다. nonce는 값마다 새로 만듭니다.
- 암호화 키는 데이터베이스 밖(환경 변수나 파일)에 둡니다.
- 암호화한 값은 키 버전(1바이트), nonce(12바이트), 암호문, 인증 태그(16바이트)를 이 순서로 담은 바이트 열 하나로 bytea 열에 저장합니다. 앞의 두 부분과 마지막 부분은 길이가 고정이므로 복호화할 때 앞 13바이트와 뒤 16바이트를 제외한 나머지가 암호문입니다. 그래서 키 버전과 nonce를 담는 열을 따로 두지 않습니다. 키를 바꾸면 새 값은 새 키로 암호화하고, 옛 값은 저장된 키 버전의 키로 복호화합니다.
- 표시 이름(`user.display_name`)은 평문으로 둡니다. 화면마다 보여 주고 사용자가 가족끼리 부르는 이름으로 수정하는 값이기 때문입니다. 구글 이름을 그대로 두면 그 이름이 평문으로 남는 한계가 있습니다.
- 로그와 오류 메시지에 위 열의 평문과 토큰 원문을 남기지 않습니다. 외부 API로 나가는 요청(지오코더에 보내는 주소 등)도 포함합니다.
- 구글의 ID 토큰과 액세스 토큰은 로그인할 때 검증에만 사용하고 저장하지 않습니다. 서버 세션의 속성에도 저장하지 않고 서비스 사용자 번호와 인증 시각(`auth_time`)만 담은 로그인 정보를 둡니다([결정 기록 0013](0013-session.md)).
- 세션 토큰과 초대 토큰은 원문을 저장하지 않고 해시만 저장합니다. 세션 토큰은 Spring Session 세션 테이블의 세션 ID 열(`spring_session.session_id`)에, 초대 토큰은 `invitation.token_hash`에 저장합니다. 해시는 SHA-256입니다. 요청에 담긴 토큰을 해시해 저장된 값과 비교합니다.
- 암호화로 막지 못하는 유출이 있습니다. 내부자나 애플리케이션 자격증명을 탈취한 사람이 정상 경로로 읽으면 복호화된 값이 보입니다. 2025년 11월 쿠팡 개인정보 유출 사례처럼 이런 유출은 암호화로 막지 못하므로 접근 통제와 감사 로그로 보완합니다. 1단계의 보완 수단은 접근 통제(데이터베이스 계정 분리와 최소 권한)뿐입니다. 감사 로그는 운영 관측이 2단계이므로(PRD 기능 범위) 2단계에 추가하고, PRD 운영 관측 범위는 2단계 계획 때 함께 수정합니다.
- 사진 파일도 위 열과 같은 방식(애플리케이션 계층 AES-GCM, 키 버전, nonce, 암호문, 인증 태그를 이 순서로 담은 바이트 열)으로 암호화해 저장하며, `storage_key`를 추가 인증 데이터(AAD)로 넣습니다. 저장소 접근 키를 탈취한 사람이 남의 암호문을 자기 사진의 오브젝트 키 위치로 옮겨 API로 다운로드해도 복호화되지 않게 하기 위해서입니다. 저장소와 업로드와 다운로드 경로는 [결정 기록 0014](0014-file-storage.md)가 정합니다. GPS 같은 메타데이터를 삭제할지와 어디서 삭제할지는 임장 기록 기능 명세에서 정합니다.
- 알림 메일 본문에는 매물 주소, 동, 호를 넣지 않습니다. 메일은 서비스 밖의 메일함에 평문으로 남기 때문입니다. 거래 알림은 단지 이름, 알림 종류(새 거래, 해제), 계약일, 전용면적, 층, 금액, 서비스 링크를, 방문 알림은 단지 이름, 방문 일시, 서비스 링크를 담습니다.

## 결과

- 데이터 모델의 열 근거 표에 열마다 저장 방식(평문, 암호화, 해시)을 적습니다. 위 결정의 대상이 아닌 열은 평문입니다.
- 세션 방식과 토큰 발급은 [결정 기록 0013](0013-session.md)에 적었습니다. 초대 링크는 해시만 저장하므로 만든 직후 한 번만 응답에 담는다는 규칙은 [API 공통 규칙](../architecture/api-conventions.md#응답에-담는-개인정보)의 응답에 담는 개인정보 절에 적었습니다.
- 키를 두는 위치의 구체 값, 키를 바꾸는 절차, 로그에서 개인정보를 가리는 방법은 구현에서 정합니다.

## 상태

확정, 2026-10-19

2026-10-20에 엔드포인트 단위 계약을 설계 문서로 작성하지 않고 기능마다 SpecKit 계획 단계에서 만들기로 해서, 엔드포인트 계약으로 넘겼던 항목의 정하는 곳을 수정했습니다.

2026-10-20에 세션을 Spring Session JDBC에 두기로 해([결정 기록 0013](0013-session.md)) 세션 토큰 해시를 저장하는 곳과 구글 토큰을 세션에도 저장하지 않는다는 문장을 수정했습니다.

2026-11-02에 알림 메일 주소 열을 두지 않기로 해([결정 기록 0010](0010-login-method.md)) 암호화 대상에서 `notification_setting.email`을 빼고, 사용하는 곳이 없는 `login_email_hash`와 HMAC 키를 뺐습니다. 같은 날 사진 파일 저장소를 정했습니다([결정 기록 0014](0014-file-storage.md)). 사진 파일 암호화(오브젝트 키를 추가 인증 데이터로 넣음)와 메일 본문에 넣지 않는 값을 정했고, 로그 규칙을 외부 API로 나가는 요청에도 적용했습니다.
