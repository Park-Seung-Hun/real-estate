# 0011. 가족 공유와 권한

기록은 가구 단위로 공유하고 역할은 owner와 member 둘을 두며, 초대는 일회용 링크로 하고, 표시 이름은 제공자 이름을 기본값으로 두고 직접 고칩니다.

## 배경

- PRD는 본인과 가족 구성원 두 명이 각자 로그인해 같은 매물과 기록을 함께 보고, 평가와 메모는 각자 남긴다고 정했습니다([PRD 사용자](../prd.md#사용자), [기능 범위](../prd.md#기능-범위)의 로그인과 가족 공유).
- [결정 기록 0010](0010-login-method.md)에 따라 외부 제공자 계정으로 로그인합니다. 구글 계정만 있으면 누구나 로그인할 수 있습니다. 그래서 누가 이 가족의 기록을 보는지는 로그인이 아니라 가족 초대로 정해야 합니다.
- [와이어프레임](../design/wireframes.md)의 가족 초대 화면은 초대 수단을 정하지 않아 입력란이 비어 있습니다. 매물 상세와 임장 기록 작성 화면에 보이는 작성자 표시 이름도 어디서 받을지 정하지 않았습니다.

이 기록에서 가구(household)는 기록을 함께 보는 사람들의 묶음이고, 멤버십은 사용자가 어느 가구에 어떤 역할로 속하는지를 뜻합니다.

## 선택지

공유 단위와 역할은 아래 세 가지를 비교했습니다.

| 선택지 | 내용 | 선택 |
|---|---|---|
| 역할 없음 | 가구 구성원 모두 같은 권한을 받습니다 | 제외. 초대 발급, 초대 취소, 구성원 제거를 아무 구성원이나 할 수 있게 됩니다 |
| owner와 member | 가구를 만든 사람(owner)만 구성원을 바꾸고, 기록은 owner와 member 둘 다 씁니다 | 채택 |
| owner, member, 읽기 전용 | 두 역할에 기록을 보기만 하는 역할을 더합니다 | 제외. PRD가 두 사람 모두 기록을 쓰게 하므로 읽기 전용 역할을 줄 사람이 없습니다 |

초대 수단은 아래 세 가지를 비교했습니다.

| 선택지 | 내용 | 잘못된 사람이 쓸 위험과 막는 방법 | 만료 | 구현 부담 | 선택 |
|---|---|---|---|---|---|
| 초대 링크 | owner가 만든 링크(URL에 일회용 토큰)를 메신저나 메일로 보내고, 받은 사람이 링크를 열어 로그인하면 수락합니다 | 링크가 다른 사람에게 넘어가면 그 사람이 먼저 수락할 수 있습니다. 한 번 수락하면 토큰을 무효로 하고, owner가 구성원 목록에서 수락한 사람을 확인해 아니면 제거합니다 | 필요합니다. 링크가 메신저 대화나 메일함에 남습니다 | 추측할 수 없는 토큰의 생성과 저장, 수락 API가 필요합니다. 로그인하지 않은 채 링크를 열면 로그인 뒤 그 링크로 돌아와야 하는데, 알림 메일의 링크에도 같은 흐름이 있습니다 | 채택 |
| 초대 코드 | owner 화면에 짧은 코드가 보이고, 말이나 메시지로 알려 주면 받은 사람이 로그인 뒤 코드를 입력합니다 | 코드가 짧아 추측하거나 옆에서 듣고 쓸 수 있습니다. 입력 시도 횟수를 제한하고 만료를 짧게 둡니다. 수락 뒤 owner가 확인하는 것은 링크와 같습니다 | 짧게 둬야 합니다. 코드가 짧을수록 추측 위험이 큽니다 | 코드 입력 화면이 하나 더 필요하고, 코드 중복 확인과 입력 시도 횟수 제한을 만들어야 합니다 | 제외. 코드가 짧아 추측을 막으려면 입력 시도 제한과 짧은 만료가 더 필요합니다 |
| 계정 지정 | owner가 상대의 이메일을 입력하고, 상대가 같은 이메일의 계정으로 로그인하면 초대가 보입니다. 제공자의 subject 값은 상대가 처음 로그인하기 전에는 서비스가 알 수 없어 지정에 쓰기 어렵습니다 | 로그인 이메일이 지정한 이메일과 같아야 수락하므로 초대가 다른 사람에게 넘어가지 않습니다. 단, 제공자가 검증했다고 표시한 이메일일 때만 이 비교를 믿을 수 있습니다 | 수락할 사람이 정해져 있어 만료가 없어도 다른 사람이 쓰지 못합니다 | 로그인에서 검증된 이메일을 받아야 합니다. 구글은 `email_verified`를 주므로 가능합니다. 상대에게 초대를 알리는 연락은 따로 해야 합니다 | 제외. 가장 안전하지만 알림 연락을 따로 해야 합니다. 로그인 뒤 링크로 돌아오는 흐름을 알림 메일에서 이미 쓰므로 링크가 구현 부담이 더 작습니다 |

작성자 표시 이름의 출처는 아래 세 가지를 비교했습니다.

| 선택지 | 내용 | 가족 두 명이 서로 알아볼 수 있는지 | 제공자가 이름을 주지 않을 때 | 개인정보 저장량 | 선택 |
|---|---|---|---|---|---|
| 제공자 프로필 이름 | 구글 계정의 이름을 그대로 씁니다 | 제공자 계정에 적힌 이름이나 닉네임이 그대로 보입니다. 가족끼리 부르는 이름과 다를 수 있고 서비스 안에서 바꾸지 못합니다 | 대신 보여 줄 값을 따로 정해야 합니다 | 제공자에게 이름이나 닉네임 동의를 받아 저장합니다. 카카오의 닉네임 동의항목은 비즈 앱이 아니어도 설정할 수 있습니다 | 제외. 제공자 이름을 서비스 안에서 바꾸지 못해 가족끼리 알아보기 어려울 수 있습니다 |
| 서비스에서 직접 입력 | 첫 로그인 때 이름을 입력합니다 | 가족이 정한 이름이라 서로 알아볼 수 있습니다 | 제공자와 관계없습니다. 대신 첫 로그인 때 이름 입력 단계가 하나 더 생깁니다 | 사용자가 입력한 이름 하나만 저장하고, 제공자에게 이름 동의를 받지 않아도 됩니다 | 제외. 첫 로그인 때 이름 입력 단계가 하나 더 생깁니다 |
| 제공자 이름을 기본값으로 두고 직접 고침 | 구글 계정의 이름을 기본값으로 두고 가족 초대 화면에서 고칩니다 | 처음에는 제공자 이름이 보이고, 알아보기 어려우면 고칩니다. 가족 초대 화면에 내 표시 이름 입력란을 둡니다 | 기본값이 비므로 직접 입력으로 넘어갑니다 | 제공자에게 이름 동의를 받고, 저장하는 것은 표시 이름 하나입니다 | 채택 |

## 결정

- 기록은 가구 단위로 공유합니다. 관심 단지, 매물, 호가 이력, 방문 일정, 임장 기록은 가구에 속하고, 그 가구의 구성원 모두가 봅니다.
- 역할은 owner와 member 둘입니다. 가구를 만든 사람이 owner가 됩니다. 읽기 전용 역할은 두지 않습니다.
- 1단계에서 한 사용자는 가구 하나에만 속합니다.
- 멤버십이 없는 계정은 로그인은 되지만 어느 가구의 기록도 보지 못합니다.
- 1단계에서 가구 구성원은 둘까지이고, 수락을 기다리는 초대는 한 번에 하나입니다. 구성원이 둘이면 초대를 만들 수 없습니다.
- 멤버십이 없는 계정도 할 수 있는 동작은 로그인, 자기 표시 이름 수정, 유효한 초대 링크로 수락하기, 가구 만들기(만드는 시점은 API 계약에서 정합니다), 탈퇴(자기 계정 삭제)뿐입니다. 이 동작들은 가구 역할이 아니라 로그인 여부와 초대 토큰의 유효성으로 허용합니다. 초대를 수락하면 그 가구의 member가 됩니다. owner는 가구를 먼저 삭제해야 탈퇴할 수 있습니다.

가구의 자원을 다루는 요청마다 사용자의 가구 역할에 아래 표의 권한 키가 허용돼 있는지 확인합니다. 권한 키는 `자원:행동` 꼴입니다. 권한 키 확인에 더해, 요청이 가리키는 자원(단지, 매물, 기록, 초대, 구성원)이 요청한 사람의 가구에 속하는지 확인하고, 자기 것만 고칠 수 있는 키(`visit_log:write`, `notification_setting:write`, `profile:write`)는 그 자원의 소유자가 요청한 사람인지도 확인합니다.

| 권한 키 | 뜻 | owner | member |
|---|---|---|---|
| `household:read` | 가구의 관심 단지, 매물, 호가 이력, 방문 일정, 임장 기록, 구성원 목록을 봅니다 | 허용 | 허용 |
| `interest_complex:write` | 단지를 임장 후보로 추가하고 뺍니다 | 허용 | 허용 |
| `listing:write` | 매물을 등록하고 고치고 지웁니다. 호가 추가, 방문 일정, 상태 변경을 포함합니다 | 허용 | 허용 |
| `visit_log:write` | 자기 임장 기록을 작성하고 고치고 지웁니다. 다른 구성원의 기록은 쓰지 못합니다 | 허용 | 허용 |
| `notification_setting:write` | 자기 알림 설정을 바꿉니다 | 허용 | 허용 |
| `profile:write` | 자기 표시 이름을 고칩니다. 멤버십이 없어도 허용합니다 | 허용 | 허용 |
| `invitation:read` | 보낸 초대 목록을 봅니다 | 허용 | 거부 |
| `invitation:create` | 초대를 발급합니다. 구성원이 둘이거나 기다리는 초대가 있으면 거부합니다 | 허용 | 거부 |
| `invitation:revoke` | 수락하기 전의 초대를 취소합니다 | 허용 | 거부 |
| `member:remove` | 다른 구성원을 가구에서 제거합니다 | 허용 | 거부 |
| `member:leave` | 스스로 가구에서 나갑니다. owner는 나가는 대신 가구를 삭제합니다 | 거부 | 허용 |
| `household:delete` | 가구와 그 가구에 속한 기록을 모두 삭제합니다. owner가 서비스를 그만둘 때 사용합니다 | 허용 | 거부 |

이 표에 없는 권한 키를 요구하는 요청은 거부합니다. 멤버십이 없는 계정의 요청도 위에 적은 "멤버십이 없는 계정도 할 수 있는 동작"을 빼고는 모두 거부합니다(기본 거부).

- 초대는 owner가 만든 일회용 링크로 합니다. 링크의 토큰은 추측할 수 없는 값이고 만료가 있으며(만료 기간은 API 계약에서 정합니다), 한 번 수락하면 무효가 됩니다. 받은 사람은 링크를 열어 로그인하면 바로 member가 되어 가구의 기록을 봅니다. 그래서 링크는 가족에게만 직접 보내야 합니다. owner는 구성원 목록에서 수락한 사람의 표시 이름과 로그인 이메일을 보고 가족이 맞는지 확인하며, 아니면 제거합니다. 여기서 보여 주는 로그인 이메일은 구글이 로그인 때 준 값이라 사용자가 서비스 안에서 고칠 수 없고, 알림 설정에서 바꿀 수 있는 알림 메일 주소와는 다른 값입니다. 구글이 검증했다고 표시한(`email_verified`가 true인) 이메일만 확인용으로 믿고, 그렇지 않으면 "검증되지 않음"을 함께 표시합니다.
- 표시 이름은 제공자 프로필 이름(구글은 `profile` scope의 `name`)을 기본값으로 저장하고, 사용자가 가족 초대 화면에서 자기 표시 이름을 고칩니다. 제공자가 이름을 주지 않으면 빈 값으로 두고 사용자가 입력합니다.

## 결과

- 데이터 모델에 가구 테이블, 멤버십 테이블(사용자, 가구, 역할), 초대 테이블(가구, 발급한 사람, 토큰의 해시(원문은 저장하지 않습니다), 상태, 만료 시각)을 둡니다. 초대 상태 값(예: 대기, 수락, 취소, 만료)도 데이터 모델에서 정합니다.
- API 계약에 초대 발급, 초대 취소, 초대 목록, 초대 수락, 구성원 목록, 구성원 제거, 가구 나가기, 가구 삭제, 탈퇴 API를 두고, API마다 필요한 권한 키나 멤버십 없이 허용하는 조건을 적습니다.
- 가구를 만드는 시점(첫 로그인 때 자동으로 만들지, 사용자가 화면에서 만들지)은 API 계약에서 정합니다. 사용자당 가구가 하나이므로, 이미 가구가 있는 사람이 초대를 수락하면 기존 가구를 어떻게 할지도 함께 정합니다.
- owner는 가구를 삭제한 뒤에 탈퇴합니다. 가구를 삭제하면 member의 임장 기록도 함께 사라지므로, 삭제 전 확인 절차는 API 계약에서 정하고 삭제 범위는 데이터 모델에서 확인합니다.
- member는 가구에서 나간 뒤에 탈퇴합니다. member가 나가거나 탈퇴할 때 그 사람의 임장 기록을 가구에 남길지 지울지, 알림 설정과 로그인 이메일 같은 계정 자료를 언제 지울지는 데이터 모델에서 정합니다.
- 와이어프레임의 가족 초대 화면에 초대 링크 만들기와 보낸 초대 목록, 내 표시 이름 입력란을 그립니다. 구성원 목록에 로그인 이메일과 검증 여부를 보여 주고, member에게는 가구 나가기를 보여 줍니다. 사용자 테이블의 표시 이름 컬럼은 [결정 기록 0010](0010-login-method.md)의 결과를 따릅니다. "정하지 않은 것" 표의 초대 수단 행과 표시 이름 행도 함께 고칩니다.
