# 0014. 사진과 원본 응답 파일 저장소

임장 기록 사진과 실거래 원본 응답은 S3 호환 오브젝트 저장소에 두고, 버킷을 둘로 나눕니다. 사진은 암호화해 늘 API 서버를 거쳐 올리고 내려 주며, 원본 응답은 gzip으로 압축해 삭제하지 않고 보관합니다.

## 배경

- [C4 컨테이너](../architecture/c4-container.md)는 사진 파일 저장소를 데이터베이스 밖의 컨테이너로 두었지만 기술과 저장 경로는 정하지 않았습니다. [데이터 모델](../architecture/data-model.md)도 `visit_photo.storage_key`의 형식, 사진 파일을 삭제하는 방법, 사진 파일 암호화를 핵심 흐름으로 넘겼습니다.
- [결정 기록 0007](0007-change-history.md)은 원본 API 응답을 데이터베이스가 아니라 파일 스냅샷으로 보관하기로 했지만, 파일을 둘 저장소와 보관 기간은 정하지 않았습니다.
- 3단계에서 Kubernetes를 도입하면 API 서버를 순차 교체로 배포하고, 서버 두 대로 실행하는 실험도 합니다([결정 기록 0004](0004-staged-adoption.md)). 이때 어느 서버가 요청을 받아도 같은 파일을 읽어야 합니다.
- 사진은 가족이 보러 다닌 집의 내부와 주변을 담습니다. 매물 주소와 동호수를 암호화하기로 한 [결정 기록 0012](0012-personal-data-storage.md)와 같은 이유로 보호가 필요합니다.
- 2026-10-20 수집분(최근 6개월)의 원본 응답은 1.59MB였고 gzip으로 압축하면 77KB였습니다. 하루 크기가 같다면 1년에 약 28MB입니다(추정).

## 선택지

| 선택지 | 내용 | 선택 |
|---|---|---|
| S3 호환 오브젝트 저장소 | 사진과 원본 응답을 S3 API로 읽고 쓰는 저장소의 버킷에 둡니다 | 채택. 서버가 몇 대든 같은 버킷을 읽습니다. 버킷마다 접근 키의 권한을 나눌 수 있고, 업체를 바꿔도 같은 API를 씁니다 |
| 서버 로컬 디스크 폴더 | 애플리케이션 서버의 디스크 폴더에 파일을 둡니다 | 제외. 3단계에 서버 두 대가 같은 파일을 보지 못합니다 |
| 데이터베이스에 바이트로 저장 | 파일 내용을 PostgreSQL의 bytea 열에 넣습니다 | 제외. C4 컨테이너와 데이터 모델이 이미 파일을 데이터베이스 밖에 두기로 했습니다 |

## 결정

- 파일은 S3 호환 오브젝트 저장소에 둡니다. 사진 버킷과 원본 응답 버킷을 나눕니다.
- API 서버의 저장소 접근 키는 사진 버킷에만, collector의 키는 원본 응답 버킷에만 권한이 있습니다. 한쪽 키를 빼앗겨도 다른 버킷의 파일은 읽거나 삭제하지 못합니다.
- 업체는 배포 환경을 정할 때 고릅니다. 저장소를 같은 서버에 직접 설치해 운영하면 백업을 따로 구성합니다.
- 파일 키는 두 가지 형식입니다.

| 버킷 | 키 형식 |
|---|---|
| 사진 | `{household_id}/{임의 UUID}`. `visit_photo.storage_key`에 이 값을 저장합니다 |
| 원본 응답 | `{수집 날짜 YYYY-MM-DD}/{실행 시작 시각 HHmmss}/{시군구 코드}-{계약년월}-p{쪽 번호}.xml.gz` |

- 원본 응답은 gzip으로 압축해 삭제하지 않고 보관합니다. 실행마다 따로 남고 덮어쓰지 않으므로, 같은 날 다시 받아도 앞 실행의 파일과 섞이지 않습니다. 위 측정대로라면 1년에 수십 MB라 1단계에서 삭제할 이유가 없습니다. 4단계(서울 전체)로 수집 범위를 넓힐 때 크기를 다시 재고 보관 기간을 다시 봅니다.
- 사진은 [결정 기록 0012](0012-personal-data-storage.md)와 같은 애플리케이션 계층 AES-GCM으로 암호화해 저장합니다. 암호화 방식은 0012가 정하며, 파일 키(`storage_key`)를 추가 인증 데이터로 넣습니다.
- 사진은 늘 API 서버를 거쳐 올리고 내려 줍니다. 저장소 주소를 화면에 주지 않습니다. 저장소에는 암호문만 있고, 화면은 API 서버의 권한 확인을 거쳐야 사진을 받습니다.
- 사진을 올릴 때는 파일을 먼저 저장하고 `visit_photo` 행을 저장합니다. 삭제할 때는 행을 삭제하는 트랜잭션이 확정된 뒤 파일을 삭제합니다. 어느 쪽이든 중간에 실패하면 행이 없는 파일이 남을 뿐, 행이 가리키는 파일이 없는 경우는 생기지 않습니다.
- 남은 파일은 API 서버의 예약 실행(사진 파일 정리)이 하루 한 번 사진 버킷만 대조해 삭제합니다. `visit_photo` 행이 없고 올린 지 하루가 지난 파일이 대상입니다. 하루를 기다리는 이유는 파일을 저장했지만 행은 아직 저장하지 않은 올리기 요청의 파일을 삭제하지 않기 위해서입니다.

## 결과

- [데이터 모델](../architecture/data-model.md)의 `visit_photo.storage_key`에 위 사진 키 형식을 적고, 원본 응답 스냅샷이 원본 응답 버킷에 있다고 고칩니다.
- [C4 컨테이너](../architecture/c4-container.md)의 사진 파일 저장소를 S3 호환 오브젝트 저장소로 고치고, collector가 원본 응답 버킷에 쓰는 관계를 그립니다.
- [C4 컴포넌트](../architecture/c4-component.md)의 매물과 기록 모듈에 들어오는 쪽 어댑터 "예약 실행(사진 파일 정리)"을 더합니다.
- 사진을 올리고 삭제하는 순서는 [핵심 흐름](../architecture/flows.md)에 그립니다.
- 사진의 GPS 같은 메타데이터를 삭제할지와 어디서 삭제할지는 임장 기록 기능 명세에서 정합니다.
- [결정 기록 0007](0007-change-history.md)과 [결정 기록 0012](0012-personal-data-storage.md)가 넘겼던 저장소와 사진 암호화를 이 기록에 맞춰 고칩니다.
