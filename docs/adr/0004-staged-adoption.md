# 0004. 단계별 기술 도입과 도입 조건

Kafka, Redis, Kubernetes는 1단계에 도입하지 않고, 3단계와 4단계를 시작할 때 도입 조건을 측정해 조건을 만족한 기술만 도입합니다.

## 배경

서비스는 [PRD 기능 범위](../prd.md#기능-범위)의 단계 순서로 만듭니다. 1단계는 임장 기록과 거래 알림을 실제 임장에 사용할 수 있는 최소 구성입니다. 3단계는 수집, 알림 발송, 배포 구조를 바꾸고, 4단계는 실거래 범위를 서울 전체로 넓힙니다. 3단계와 4단계 기능에는 아래 요구가 있습니다.

| 기능(단계) | 요구 |
|---|---|
| 거래 변경 이벤트 분리(3) | 거래 변경(신규, 해제, 정정)을 받는 쪽(집계 갱신, 알림)마다 속도와 실패 양상이 다릅니다. 알림 규칙을 바꾸면 지난 이벤트를 다시 읽어 알림 대상을 다시 계산해야 합니다 |
| collector와 알림 발송기 분리, 무중단 배포(3) | API 서버, collector, 알림 발송기의 실패 양상과 배포 주기가 다릅니다. 배포하는 동안에도 알림을 계속 보내야 합니다 |
| 작업 중복 실행 방지와 호출 제한(3) | 서버를 두 대로 실행할 때 수집 작업이 두 번 실행되지 않아야 합니다. 외부 API마다 하루 호출 한도를 지켜야 합니다 |
| 조회 성능(4) | 실거래를 서울 전체 10년치로 넓히면 단지별 추이 조회가 느려질 수 있습니다 |

PRD는 3단계와 4단계의 기술을 도입하기 전에 도입 조건을 측정하고, 그 결과를 결정 기록에 남기기로 했습니다. 이 기록은 기술마다 무엇을 측정해 어떤 기준이면 도입할지 정합니다.

## 선택지

| 선택지 | 내용 | 선택 |
|---|---|---|
| 1단계부터 사용 | Kafka, Redis, Kubernetes를 1단계 구성에 도입합니다 | 선택하지 않음. 세 기술이 맡을 요구는 PRD에서 3단계와 4단계 기능으로 정했습니다 |
| 해당 단계를 시작할 때 조건을 측정하고 사용 | 3단계와 4단계를 시작할 때 결정 절의 도입 조건을 측정하고, 조건을 만족한 기술만 도입합니다 | 채택 |
| 사용하지 않음 | Kafka 대신 PostgreSQL 테이블로 거래 변경을 전달합니다. Redis 대신 PostgreSQL에 락과 호출 횟수를 두고, 단지 추이 조회는 인덱스, 파티셔닝, 집계 테이블로 개선합니다. Kubernetes 없이 배포합니다 | 측정 결과 조건을 만족하지 못한 기술에 적용합니다 |

## 결정

세 기술은 아래 단계를 시작할 때 도입 조건을 측정하고, 조건을 만족한 기술만 도입합니다.

| 기술 | 단계 | 맡는 요구 | 측정 | 도입 기준 |
|---|---|---|---|---|
| Kafka | 3 | 거래 변경 이벤트 분리 | 같은 양의 거래 변경 이벤트로 PostgreSQL 테이블 방식과 Kafka를 각각 적용해 두 시간을 측정합니다. 하나는 알림 쪽을 멈춘 동안 집계 갱신이 늦어진 시간이고, 다른 하나는 알림 규칙을 바꾼 뒤 지난 이벤트로 알림 대상을 다시 계산하는 데 걸린 시간입니다 | PostgreSQL 테이블 방식에서 두 시간 중 하나라도 기준을 넘고, Kafka에서는 둘 다 기준 안에 들면 도입합니다 |
| Kubernetes(k3s) | 3 | collector와 알림 발송기 분리, 무중단 배포 | 같은 변경을 k3s 없이 배포할 때와 k3s로 배포할 때(collector는 예약 작업, API 서버는 순차 교체)의 두 값을 측정합니다. 배포하는 동안 실패한 요청 수와 알림 발송이 멈춘 시간입니다 | k3s 없이 배포할 때 두 값 중 하나라도 기준을 넘고, k3s로 배포할 때는 둘 다 기준 안에 들면 도입합니다 |
| Redis(락과 호출 제한) | 3 | 작업 중복 실행 방지와 호출 제한 | 서버를 두 대로 실행해, 락이 없을 때 같은 수집 범위(지역과 월)가 두 번 실행되는지 재현합니다. 그다음 락과 호출 횟수를 PostgreSQL에 둔 경우와 Redis에 둔 경우를 각각 실행해, 중복 실행 횟수와 하루 한도를 넘긴 호출 수를 셉니다 | PostgreSQL 방식에서 중복 실행이나 한도 초과가 한 번이라도 생기고, Redis 방식에서는 생기지 않으면 도입합니다. 락이 없을 때 중복 실행이 재현되지 않으면 락은 도입하지 않습니다 |
| Redis(캐시) | 4 | 조회 성능 | 서울 전체 10년치 실거래로 단지별 추이 조회의 응답 시간을 부하 실험으로 측정합니다. 인덱스, 파티셔닝, 집계 테이블, 캐시를 같은 부하에서 각각 적용합니다 | 응답 시간이 기준 안에 드는 방법 중에서 고릅니다. 캐시를 고를 때만 Redis를 캐시로 사용합니다 |

- 표의 "도입 기준"에 들어갈 시간과 요청 수는 측정한 뒤 정하고, 측정 결과와 기준값을 새 결정 기록에 적습니다. Redis 락과 호출 제한의 기준(중복 실행과 한도 초과가 없음)은 PRD의 요구 그대로입니다.
- 측정 결과 도입하지 않는 쪽이 맞으면 그 결정도 결정 기록으로 남기고, 선택지 표의 "사용하지 않음" 방식을 적용합니다.
- 운영 관측(2단계)의 도구는 도입 조건을 따로 측정하지 않고 2단계에 도입합니다. 운영 관측은 PRD에서 2단계 기능으로 정했고, 매일 실행하는 수집과 알림 발송의 지연, 누락, 실패를 봐야 하기 때문입니다. 도구는 OpenTelemetry, Prometheus, Loki, Grafana, Alertmanager이고, 추적 저장소는 정하지 않았습니다.

## 결과

- [C4 컨테이너](../architecture/c4-container.md)의 1단계 구성에는 Kafka, Redis, Kubernetes가 없습니다. 목표 구성은 세 기술이 모두 조건을 만족했을 때의 구성입니다.
- 도입하지 않기로 한 기술이 생기면 C4 컨테이너의 목표 다이어그램을 그 결정에 맞춰 고칩니다.
- 3단계와 4단계는 도입 조건 측정부터 시작합니다. 측정하려면 같은 부하를 재현하는 실험과, 비교 대상인 PostgreSQL 방식의 구현이 필요합니다.
- k3s 클러스터 안에서 PostgreSQL, Kafka, Redis, 관측 구성을 실행할지는 배포 환경([PRD 열린 질문](../prd.md#열린-질문))을 정할 때 결정합니다.
